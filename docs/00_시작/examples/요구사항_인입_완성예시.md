# 요구사항 인입 완성 예시

이 문서는 사용자가 작성해야 하는 빈 Template이 아니라 `harness.py intake`가 어떤 결과를 만드는지 보여주는 예시다.

## 입력 예시

| Level1 | Level2 | 요구사항 ID | 요구사항명 | 요구사항 |
|---|---|---|---|---|
| 휴가관리 | 신청 | REQ-LEAVE-001 | 휴가 신청 개선 | 직원이 휴가를 신청한다 |
| 휴가관리 | 신청 | REQ-LEAVE-002 | 휴가 신청 개선 | 잔여 휴가일수를 확인한다 |

사용자는 이 표를 Harness Template으로 다시 옮겨 적지 않는다. 원본 XLSX를 그대로 제공한다.

## 실행

```bash
python sdlc/scripts/harness.py intake requirements.xlsx
```

## Canonical Candidate 예시

- `RQ-001`
  - 이름: 휴가 신청 개선
  - 업무영역: 휴가관리 / 신청
  - 원본 외부 ID: REQ-LEAVE-001, REQ-LEAVE-002
  - 현재 문제: OPEN
  - 원하는 결과: OPEN
  - 업무 규칙: OPEN
  - 상태: CANDIDATE
- `FR-001`: 직원이 휴가를 신청한다 — CANDIDATE
- `FR-002`: 잔여 휴가일수를 확인한다 — CANDIDATE

원본 Sheet/Row와 Source Hash는 Provenance로 보존한다. 같은 이름으로 묶였다는 사실만으로 승인된 업무 분해가 되지는 않는다.

## 사람에게 보여줄 질문

- 같은 이름으로 묶인 두 행을 하나의 변경 단위로 보는 것이 맞는가?
- 승인 정책·대상 범위·예외 규칙은 추가 Evidence에서 확인 가능한가, 아니면 업무 담당자의 결정이 필요한가?
- 원문만으로 확인할 수 없는 기대 결과를 누가 확정할 것인가?

사람이 수십 개 placeholder를 처음부터 채우는 것이 기본 절차가 아니다.

## 다음 작업

Intake 결과가 반환한 Target을 사용한다.

```bash
python sdlc/scripts/harness.py work --target RQ-001
```

`/work`는 Change Level과 현재 Evidence에 따라 필요한 최소 Semantic Work를 선택하고 Engineering Projection을 작성/보완한다. 근거 없는 업무 정책·범위·승인 조건은 OPEN으로 유지한다.

## 결과 분리

- 사용자 확인 View: `docs/00_관리/요구사항_인입결과.md`
- Machine Runtime: `sdlc/runtime/intake/...`
- Canonical Store: `sdlc/canonical/store.json`
- Engineering 결과: 선택된 Engineering Profile의 Artifact (`ENGINEERING_SDD_COMPACT` 기본)

사용자는 Machine JSON을 직접 편집하지 않는다.
