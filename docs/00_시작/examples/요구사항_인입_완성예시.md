# 요구사항 인입 결과 예시

이 문서는 사용자가 작성하는 빈 Template이 아니라 `harness.py intake` 후 사람이 어떤 결과를 확인하는지 보여주는 예시다.

## 입력 예시

| Level1 | Level2 | 요구사항 ID | 요구사항명 | 요구사항 |
|---|---|---|---|---|
| 휴가관리 | 신청 | REQ-LEAVE-001 | 휴가 신청 개선 | 직원이 휴가를 신청한다 |
| 휴가관리 | 신청 | REQ-LEAVE-002 | 휴가 신청 개선 | 잔여 휴가일수를 확인한다 |

사용자는 이 표를 Harness 전용 양식으로 다시 옮겨 적지 않고 원본 XLSX를 그대로 제공한다.

## 실행

```bash
python sdlc/scripts/harness.py intake requirements.xlsx
```

## 사람이 확인하는 결과 예시

```text
RQ-001  휴가 신청 개선

원본 요구 ID
- REQ-LEAVE-001
- REQ-LEAVE-002

현재 확인된 요구
- 직원이 휴가를 신청할 수 있어야 한다.
- 잔여 휴가일수를 확인할 수 있어야 한다.

추가 확인이 필요한 내용
- 두 원본 요구를 하나의 작업 단위로 보는 것이 맞는가
- 승인 정책은 무엇인가
- 적용 대상과 예외는 무엇인가
- 완료 판단 기준은 무엇인가
```

원본 Sheet/Row와 Hash 같은 기술 추적정보는 Runtime이 보존하지만 일반 사용자가 직접 편집할 필요는 없다.

같은 이름으로 묶였다는 이유만으로 승인된 업무정책이나 상세 설계를 자동 확정하지 않는다.

## 다음 작업

Intake가 반환한 실제 Target을 사용한다.

```bash
python sdlc/scripts/harness.py work --target RQ-001
```

`/work`에서 Agent가 관련 Source·문서·DB·Config를 조사하고 확인 가능한 내용으로 Engineering 문서를 보완한다. 근거가 없는 정책·범위·승인 조건은 추가 확인이 필요한 내용으로 남긴다.

## 결과 위치 예

```text
docs/00_관리/요구사항_인입결과.md
docs/00_관리/RQ_생성근거.md
sdlc/runtime/intake/...
sdlc/canonical/store.json
```

사람은 `docs/00_관리`의 View를 우선 보고 Machine JSON을 직접 수정하지 않는다.
