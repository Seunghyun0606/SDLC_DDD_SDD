# 프로젝트 개발가이드 적용 가이드

## 1. 목적

프로젝트마다 Java/JSP/DB/SQL/Test/Security/배포 방식과 금지사항이 다르다. 이 문서는 그런 프로젝트별 개발 가이드를 어디에 두고 Agent가 언제 읽어야 하는지 설명한다.

핵심 원칙은 다음과 같다.

```text
반드시 지켜야 하는 규칙/금지사항
→ sdlc/custom/project/rules/

개발자가 참고하고 따라야 하는 개발표준/가이드
→ sdlc/custom/project/standards/

고객이 제공한 원본 PDF/DOCX/XLSX
→ br-input/originals/
```

## 2. 권장 폴더 구조

```text
sdlc/custom/project/
├─ rules/
│  ├─ architecture-rule.mdc
│  ├─ tool-usage.mdc
│  └─ security-rule.mdc
└─ standards/
   ├─ README.md
   ├─ java-coding-guide.md
   ├─ jsp-development-guide.md
   ├─ database-guide.md
   ├─ sql-guide.md
   ├─ test-guide.md
   └─ deployment-guide.md
```

### rules

현재 작업에 적용되는 내용이면 Agent가 반드시 따라야 한다.

예:

- Controller에서 DB 직접 접근 금지
- SQL은 프로젝트 지정 XML Mapper에만 작성
- 공통 인증 API를 우회하지 않음
- DB 조회는 지정된 DB MCP를 우선 사용
- Java 영향분석은 프로젝트 정적분석 Tool을 우선 사용
- 운영 DB 변경 명령 실행 금지

### standards

설계/개발/테스트 방법을 설명하는 개발 가이드다.

예:

- Java Naming/Exception/Transaction 표준
- JSP/JavaScript 화면개발 방식
- SQL 작성 규칙
- DB Object Naming
- 단위/통합테스트 기준
- 배포 및 Rollback 절차

## 3. 고객이 기존 개발표준 문서를 제공한 경우

원본 문서는 삭제하거나 Harness 형식으로 억지 변환하지 않는다.

```text
br-input/originals/개발표준_v3.pdf
br-input/originals/DB표준.docx
```

처럼 보존한다.

Agent가 반복적으로 따라야 하는 확정 규칙은 읽기 쉬운 Markdown으로 정리해서 다음에 둔다.

```text
sdlc/custom/project/standards/java-coding-guide.md
sdlc/custom/project/standards/database-guide.md
```

반드시 위반해서는 안 되는 내용은 별도로 짧게 추려 다음에 둔다.

```text
sdlc/custom/project/rules/architecture-rule.mdc
```

원본과 정리본이 충돌하면 Agent가 임의로 하나를 정답으로 선택하지 않고 확인이 필요한 사항으로 알린다.

## 4. Agent가 읽는 순서

`/work`를 시작하면 다음 순서를 따른다.

```text
.sdlc/project.yaml
→ Core work Skill / Stage Reference
→ sdlc/custom/project/rules/의 현재 작업 적용 규칙
→ sdlc/custom/project/standards/의 관련 개발가이드
→ 필요 시 Domain rules/standards
→ 관련 Source/DB/Test 근거
→ 설계/개발/테스트
```

`rules/`는 현재 작업에 적용되면 필수로 읽는다.

`standards/`는 모든 파일을 매번 읽지 않는다. 현재 Stage와 변경 범위에 필요한 문서만 선택한다.

예:

```text
Java Service 수정
→ java-coding-guide.md
→ database-guide.md (DB 사용 시)
→ test-guide.md

JSP 화면 수정
→ jsp-development-guide.md
→ java-coding-guide.md (Backend 변경 시)
→ test-guide.md

DB Procedure 변경
→ database-guide.md
→ sql-guide.md
→ test-guide.md
```

## 5. Domain 공통 가이드와 Project 가이드 구분

여러 프로젝트에서 재사용할 Domain별 규칙은 다음에 둘 수 있다.

```text
sdlc/custom/domain/hris/
├─ rules/
├─ standards/
├─ templates/
└─ config/
```

예:

```text
모든 HRIS 프로젝트에서 공통으로 사용하는 근태 Domain 설계 규칙
→ sdlc/custom/domain/hris/standards/

현재 고객사에서만 사용하는 Java/DB 개발 방식
→ sdlc/custom/project/standards/
```

Project 규칙이 현재 프로젝트에 대한 더 구체적인 규칙이면 Project 규칙을 우선한다. 단 Core Harness의 안전/추적성 규칙을 제거할 수는 없다.

## 6. Tool 사용 가이드

정적분석 Tool, DB MCP 등 프로젝트 Tool을 반드시 사용하게 하려면 역할을 분리한다.

```text
sdlc/custom/project/rules/tool-usage.mdc
→ 언제 어떤 Tool을 반드시 사용해야 하는지

sdlc/custom/project/standards/tools/static-analysis.md
→ Tool의 사용 방법과 결과 해석

sdlc/custom/project/standards/tools/db-mcp.md
→ DB MCP의 조회 범위, 읽기 전용 여부, 결과 해석
```

Credential, Password, Token 등 비밀정보는 Repository 문서에 넣지 않는다.

## 7. 작성 방법

개발 가이드는 Agent와 개발자가 함께 읽기 쉽도록 다음 형식을 권장한다.

```text
# Java 개발 가이드

## 적용 범위
어떤 Source/모듈에 적용되는지

## 반드시 지킬 내용
MUST 규칙

## 권장 방식
SHOULD 규칙

## 예외
어떤 경우 예외가 가능한지

## 확인 방법
정적분석/Build/Test 등 검증 방법
```

가이드에는 프로젝트에서 실제로 사용하는 용어와 경로를 사용한다. 예제 Framework 값을 그대로 복사하지 않는다.

## 8. 현재 Framework 점검 결과

현재 `/work`의 Runtime `work-context.json`에는 Project Config에서 파생된 `project_context`가 들어가지만 `sdlc/custom/project/rules/`와 `standards/` 파일 내용 전체를 자동으로 주입하지는 않는다.

전체 개발가이드를 Runtime JSON에 넣으면 Context가 과도하게 커질 수 있기 때문에 다음 정책을 사용한다.

```text
Host Agent 공통 규칙
→ rules/ 존재 시 현재 작업 적용 규칙 확인

Work Skill
→ 현재 Stage/기술/변경범위에 필요한 standards만 선택

Runtime
→ Source root / build / test / project config 등의 실행 경계 제공
```

Cursor에서는 `.cursor/rules/10-project.mdc`, Vendor-neutral Agent에서는 `AGENTS.md`, Claude Code에서는 `CLAUDE.md`에서 이 로딩 규칙을 명시한다.

따라서 프로젝트 팀은 개발가이드를 `standards/`에 넣기만 하고, 반드시 지켜야 하는 핵심 내용은 `rules/`에도 짧게 분리하는 방식을 권장한다.

## 9. 가장 간단한 기준

```text
"어떻게 개발하면 좋은가?"
→ standards/

"반드시 이렇게 해야 한다 / 하면 안 된다"
→ rules/

"고객이 준 원본 자료다"
→ br-input/originals/

"여러 프로젝트에서 재사용하는 Domain 공통 규칙이다"
→ sdlc/custom/domain/<domain>/
```
