# RQ 작업목록 운영 가이드

## 1. 목적

PM과 이해관계자가 Requirement Intake 이후 RQ를 배정하고, 프로젝트 전체 RQ의 현재 진행상태와 다음 작업을 한 화면에서 확인하는 방법을 설명한다.

**프로그래밍 명령에 익숙하지 않은 PM은 Excel/CSV를 기본 관리 화면으로 사용한다.**

```text
Canonical RQ                -> 요구사항 ID/명칭/외부 요구 ID
PM Planning File            -> PM이 자유롭게 정한 컬럼과 값
Runtime Check/Delivery/View -> 현재 상태/Change Level/결정 필요/검증/산출물 상태/다음 작업
                           ↓
                docs/00_관리/RQ_작업목록.md
```

Business Truth의 권위는 계속 `sdlc/canonical/store.json`이며, PM 파일의 어떤 컬럼도 Canonical을 변경하지 않는다.

## 2. PM 권장 사용법: Excel Export → 편집 → Import

### 2.1 최초 파일 만들기

Requirement Intake 후 다음 명령을 한 번 실행하거나 Agent에게 **"PM용 RQ 작업관리 엑셀 만들어줘"**라고 요청한다.

```bash
python sdlc/scripts/harness.py rq-list export \
  --format xlsx \
  --output docs/00_관리/RQ_작업관리.xlsx
```

CSV가 편하면 다음처럼 사용한다.

```bash
python sdlc/scripts/harness.py rq-list export \
  --format csv \
  --output docs/00_관리/RQ_작업관리.csv
```

### 2.2 PM이 파일에서 관리

기본 식별/참고 컬럼은 다음과 같다.

| 컬럼 | 수정 여부 | 의미 |
|---|---|---|
| RQ | 수정 금지 | Harness의 RQ 식별자 |
| 요구사항명 | 조회용 | Canonical 현재 요구사항명 |
| 외부 요구ID | 조회용 | 고객 원본 요구 ID |

이 세 컬럼 뒤에는 PM이 원하는 컬럼을 자유롭게 만들 수 있다.

예:

```text
RQ | 요구사항명 | 외부 요구ID | 담당개발자 | 업무담당 | 고객담당 | 우선순위 | Sprint | 목표배포일 | 이슈 | PM메모
```

다른 프로젝트에서는 아래처럼 달라도 된다.

```text
RQ | 요구사항명 | 외부 요구ID | 파트 | PL | 개발1 | 개발2 | QA | 고객확정자 | 계약WBS | 진척회의메모
```

즉 `담당개발자`, `Sprint`, `계약WBS` 같은 컬럼은 Framework가 미리 알아야 하는 고정 Schema가 아니다.

### 2.3 편집 결과 반영

```bash
python sdlc/scripts/harness.py rq-list import docs/00_관리/RQ_작업관리.xlsx
```

또는 Agent에게 다음처럼 요청한다.

```text
RQ_작업관리.xlsx에 PM이 수정한 내용을 반영해서 RQ 작업목록을 갱신해줘.
```

Import 후 다음 파일이 갱신된다.

```text
.sdlc/management/rq-planning.json       # PM 계획정보
sdlc/runtime/management/rq-worklist.json # Runtime 합성 결과
docs/00_관리/RQ_작업목록.md             # 이해관계자가 보는 View
```

## 3. 컬럼 추가/삭제 정책

PM 파일의 컬럼 구성을 **PM 관리 Schema**로 본다.

- 새 컬럼을 추가하고 Import → PM 관리 컬럼 추가
- 컬럼을 삭제하고 Import → 해당 PM 관리 컬럼 제거
- 셀을 비우고 Import → 해당 RQ의 그 값을 비움
- 행의 RQ를 임의로 새로 생성 → 금지. 먼저 Requirement Intake 필요

기본 Import는 파일의 PM 컬럼 구성을 현재 Schema로 교체한다.

부분 파일을 이용해 일부 컬럼만 추가하고 기존 컬럼을 보존하려면 고급 옵션을 사용한다.

```bash
python sdlc/scripts/harness.py rq-list import 일부수정.csv --merge-columns
```

## 4. PM 컬럼과 System 컬럼은 분리한다

다음 상태는 PM이 직접 입력하는 값이 아니다.

| 자동 파생 컬럼 | 의미 |
|---|---|
| 현재 상태 | 현재 SDLC 작업상태 |
| Change Level | 현재 변경 영향 수준 |
| 사람 결정 필요 | OPEN/결정 필요 건수 |
| 확보된 검증근거 | BUILD/TEST/REGRESSION/VERIFY/ACCEPTANCE 등 |
| 산출물 View | 현재/검토대기/현행화 필요 |
| 다음 작업 | 현재 가장 먼저 해야 할 행동 |

PM이 우연히 `현재 상태`라는 이름의 자체 컬럼을 만들 수도 있다. 이 경우 값 자체는 허용하지만 Generated View에서는 `PM:현재 상태`처럼 표시하여 Runtime의 `현재 상태`와 구분한다.

핵심은 다음이다.

```text
PM 파일 = 배정·일정·WBS·메모 등 Project Management 정보
Canonical = 요구사항/업무 의미
Runtime = 실제 Evidence 기반 진행상태
```

서로 자동 덮어쓰지 않는다.

## 5. 기존 CLI 배정 방식

기존 자동화나 고급 사용자를 위해 단일 RQ CLI도 유지한다.

```bash
python sdlc/scripts/harness.py rq-list assign \
  --target RQ-001 \
  --engineering-owner "박개발" \
  --test-owner "최QA" \
  --priority HIGH
```

다만 일반 PM에게는 Excel/CSV 방식을 권장한다.

## 6. 최초 Intake 후 요구사항이 추가된 경우

새 요구사항 파일 또는 갱신된 요구사항 파일을 다시 Intake한다.

```bash
python sdlc/scripts/harness.py intake 요구사항목록_추가.xlsx
```

Project RQ List는 RQ ID 기준으로 다시 합성되므로:

- 기존 RQ의 PM 정보는 유지한다.
- 새 RQ는 자동으로 새 행에 나타난다.
- 다음 Export 시 새 RQ가 PM Excel/CSV에도 포함된다.
- 삭제/취소 같은 업무 의미는 목록 행을 지우는 방식이 아니라 `/change`에서 의미적으로 처리한다.

## 7. 각 RQ 진척 확인

전체 목록:

```bash
python sdlc/scripts/harness.py rq-list refresh
```

특정 RQ 상세:

```bash
python sdlc/scripts/harness.py check RQ-001
```

프로젝트 전체 Control View:

```bash
python sdlc/scripts/harness.py check project
```

RQ의 사람용 상태는 대략 다음 흐름으로 보인다.

```text
작업 준비
→ 사람 결정 대기 (필요한 경우)
→ 개발·검증 진행
→ 고객 인수 대기
→ 배포 대기
→ 배포완료·AS-BUILT 대기
→ 완료·현행화
```

별도로 Build/Test/Regression/Technical Verify/Customer Acceptance/Deployment/AS-BUILT Evidence가 축적된다. 따라서 근거 없는 `진척률 80%`보다 **통과한 Gate와 남은 다음 작업**을 우선한다.

## 8. RQ와 참고문서 연결

PM/BA가 작업 전에 어떤 규정·회의록·업무문서를 참고해야 하는지 지정하려면 `13_RQ_참고문서_레지스트리_가이드.md`를 사용한다.

## 9. 하지 말아야 할 것

- `현재 상태`를 PM이 수동으로 DONE 처리하지 않는다.
- PM Excel 값을 바꿔 Requirement/Business Rule을 변경했다고 간주하지 않는다.
- 새 요구사항을 기존 RQ 행에 임의로 덧붙이지 않는다. Intake한다.
- 고객 정책 변경을 단순 PM 메모로 끝내지 않는다. `/change`로 Canonical에 반영한다.
- Framework용 `framework/management/전체작업목록.*`을 프로젝트 RQ List로 재사용하지 않는다.
