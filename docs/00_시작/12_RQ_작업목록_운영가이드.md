# RQ 작업목록 운영 가이드

## 1. 목적

PM과 이해관계자가 Requirement Intake 이후 RQ를 배정하고, 프로젝트 전체 RQ의 현재 진행상태와 다음 작업을 한 화면에서 확인하는 방법을 설명한다.

Project RQ List는 다음 세 정보를 합성한 **Generated Management View**다.

```text
Canonical RQ                -> 요구사항 ID/명칭/외부 요구 ID
PM Planning Store           -> 담당자/우선순위/마일스톤/계획일/비고
Runtime Check/Delivery/View -> 현재 상태/Change Level/결정 필요/검증/산출물 상태/다음 작업
```

Business Truth의 권위는 계속 `sdlc/canonical/store.json`이며, RQ List에서 진행상태를 사람이 임의로 완료 처리하지 않는다.

## 2. 생성 위치

사람이 보는 목록:

```text
docs/00_관리/RQ_작업목록.md
```

PM이 직접 관리하는 계획정보:

```text
.sdlc/management/rq-planning.json
```

Runtime 합성 결과:

```text
sdlc/runtime/management/rq-worklist.json
```

일반 사용자는 JSON 파일을 직접 편집하지 않고 Harness 명령을 사용한다.

## 3. Intake 이후 목록 생성

프로젝트 Setup이 된 상태에서 Requirement Intake를 실행하면 RQ List 갱신도 함께 시도한다.

```bash
python sdlc/scripts/harness.py intake 요구사항목록.xlsx
```

언제든 수동으로 최신 상태를 다시 만들 수 있다.

```bash
python sdlc/scripts/harness.py rq-list refresh
```

## 4. PM이 RQ를 담당자에게 배정하는 방법

예:

```bash
python sdlc/scripts/harness.py rq-list assign \
  --target RQ-001 \
  --pm-owner "김PM" \
  --business-owner "이BA" \
  --engineering-owner "박개발" \
  --test-owner "최QA" \
  --customer-decision-owner "고객 인사팀" \
  --priority HIGH \
  --milestone "M1" \
  --planned-start "2026-09-10" \
  --planned-end "2026-09-18"
```

일부 항목만 바꿔도 된다.

```bash
python sdlc/scripts/harness.py rq-list assign --target RQ-001 --engineering-owner "새 담당자"
```

배정 변경은 Requirement/Business Rule 의미를 바꾸지 않으므로 Canonical Business Truth Revision을 올리지 않는다.

## 5. 목록 컬럼

| 컬럼 | 관리 주체 | 의미 |
|---|---|---|
| RQ | Canonical | 내부 RQ ID |
| 요구사항명 | Canonical | 현재 요구사항 명칭 |
| 외부 요구ID | Canonical/Intake | 고객 원본 요구 ID |
| 우선순위 | PM | 프로젝트 우선순위 |
| PM | PM | PM 담당자 |
| 업무/BA | PM | 업무 분석/정책 확인 담당 |
| 설계·개발 | PM | 설계/개발 주 담당 |
| 테스트 | PM | 테스트 담당 |
| 고객 결정자 | PM | 고객 측 의사결정 Authority |
| 마일스톤 | PM | Release/Sprint/Milestone 등 프로젝트 묶음 |
| 계획시작 | PM | 계획 시작일 |
| 계획종료 | PM | 계획 종료일 |
| 현재 상태 | Runtime 파생 | 작업 준비/사람 결정 대기/개발·검증 진행/인수 대기/완료·현행화 등 |
| Change Level | Runtime 파생 | 현재 유효 Change Level |
| 사람 결정 필요 | Runtime 파생 | OPEN/결정 필요 건수 |
| 확보된 검증근거 | Runtime 파생 | BUILD/TEST/REGRESSION/VERIFY/ACCEPTANCE 등 확보된 Evidence |
| 산출물 View | Runtime 파생 | 현재/검토 대기/현행화 필요 |
| 다음 작업 | Runtime 파생 | 현재 상태에서 가장 먼저 해야 할 행동 |
| 비고 | PM | 프로젝트 관리 메모 |

핵심은 **계획값과 실행상태를 분리**하는 것이다. PM은 계획/배정을 관리하고, 실제 완료/검증 상태는 Evidence에서 계산한다.

## 6. 최초 Intake 후 요구사항이 추가된 경우

새 요구사항 파일 또는 갱신된 요구사항 파일을 다시 Intake한다.

```bash
python sdlc/scripts/harness.py intake 요구사항목록_추가.xlsx
```

Intake는 기존 `intake_stable_key`와 외부 요구 ID/원본 행을 이용해 기존 RQ를 재사용하고 새 RQ에는 새 ID를 부여한다. 기존 `CONFIRMED_BUSINESS`는 재-Intake 자료로 낮추거나 덮어쓰지 않는다.

Project RQ List는 RQ ID 기준으로 다시 합성되므로:

- 기존 RQ의 PM 배정/계획정보는 유지한다.
- 새 RQ는 자동으로 새 행에 나타난다.
- 삭제/취소 같은 업무 의미는 목록 행을 지우는 방식이 아니라 `/change`에서 의미적으로 처리한다.

## 7. 각 RQ 진척 확인

전체 목록:

```bash
python sdlc/scripts/harness.py rq-list refresh
```

특정 RQ 상세:

```bash
python sdlc/scripts/harness.py check RQ-001
```

프로젝트 전체 Control View:

```bash
python sdlc/scripts/harness.py check project
```

RQ List의 `현재 상태`는 수동 퍼센트가 아니라 다음 Evidence를 기반으로 파생한다.

```text
사람 결정 필요
개발 시작
Build
Test
Regression
Technical Verify
Customer Acceptance
Deployment
AS-BUILT Reconciliation
Projection Freshness
```

따라서 “진척률 80%”처럼 근거 없는 숫자보다 현재 통과한 Gate와 다음 Action을 보여주는 방식이 기본이다.

## 8. 산출물이나 Source가 바뀌었을 때

`rq-list refresh`는 현재 Canonical/Delivery/Projection metadata를 다시 읽는다. Source 자체가 변경되었다면 먼저 Brownfield Source Drift/`/work`를 통해 Evidence를 최신화한 뒤 목록을 갱신해야 한다.

```text
Source 변경
-> Drift/Impact 재확인
-> /work로 Evidence/AS-BUILT 갱신
-> Projection 재생성
-> rq-list refresh
```

Source 변경 사실만으로 Business Truth를 자동 변경하지 않는다.

## 9. 하지 말아야 할 것

- `현재 상태`를 PM이 수동으로 DONE으로 입력하지 않는다.
- RQ List의 문장을 수정해서 Requirement 의미를 변경하지 않는다.
- 새 요구사항을 기존 RQ 행에 임의로 덧붙이지 않는다. Intake한다.
- 고객 정책 변경을 단순 비고로 끝내지 않는다. `/change`로 Canonical에 반영한다.
- Framework용 `framework/management/전체작업목록.*`을 프로젝트 RQ List로 재사용하지 않는다.
