# 고객문서 작성·미리보기·현행화 가이드

이 문서는 현재까지 확인된 요구사항·업무 기준·설계·개발·테스트 근거를 이용해 **고객용 문서를 만들고 계속 최신화하는 방법**을 설명한다.

고객문서 생성은 새로운 업무정책을 확정하는 작업이 아니다. 확인된 사실만 고객이 읽기 쉬운 한국어로 표현한다.

## 1. 기본 Customer Profile

신규 프로젝트 기본값은 `CUSTOMER_STANDARD_3`다.

```text
solution_agreement
→ A01_요구_업무_기능_합의서.md

delivery_scope
→ A02_영향_개발범위_공유서.md

acceptance_handover
→ A03_테스트_인수_운영_결과서.md
```

기본 출력:

```text
docs/20_고객/<RQ>/
```

Project Custom Profile이 1/5/8/13/N종이면 실제 Profile의 artifact 구성을 따른다. Customer 문서 수를 Engineering 문서 수에 맞추지 않는다.

## 2. 가장 쉬운 사용법

Agent에게 자연어로 요청한다.

```text
RQ-001 고객문서 만들어줘.
RQ-001 고객문서 최신화해줘.
A01 다시 만들어줘.
A02 영향범위 문서 최신화해줘.
A03 테스트/인수 문서 만들어줘.
고객문서가 최신인지 확인해줘.
```

Cursor에서는 `/customer-view`, 다른 Agent에서는 `sdlc/agent/skills/customer-view/SKILL.md`의 같은 규칙을 사용한다.

현재 근거 기준으로 Profile에 정의된 고객문서를 계속 현행화하려면:

```text
/customer-view refresh RQ-001
```

상태만 확인하려면:

```text
/customer-view status RQ-001
```

저수준 CLI에서 한 문서를 직접 생성할 수도 있다.

```bash
python sdlc/scripts/harness.py customer-view \
  --target RQ-001 \
  --type solution_agreement
```

공식 `harness.py customer-view`는 고객문서를 생성하기 전에 기존 검토상태와 사람 수정 여부를 확인하는 안전 경계를 사용한다. 고객이 최종 검토한 정식 문서나 사람이 직접 수정한 정식 문서는 자동으로 덮어쓰지 않는다.

`harness.py customer-view`는 근거를 안전하게 조립하는 Runtime이고, `/customer-view` Skill은 Lifecycle 확인·도메인 용어 적용·고객 친화 문장 작성까지 포함한다.

## 3. 고객문서 작성 원칙

고객에게 특별히 요구되지 않았다면 본문에 다음 구현 식별자를 그대로 나열하지 않는다.

```text
JSP / Java / XML / SQL
Class / Method / Controller / Service / DAO / Mapper
Query ID
Table / Column
파일 경로 / Hash
내부 Runtime 상태 코드
```

기술 근거에서 업무 의미가 확인되면 고객이 이해할 수 있는 문장으로 바꾼다.

```text
기술식 표현:
WorkPlanService.savePlan()에서 EMP_WORK_PLAN 저장

고객용 표현:
근무계획을 등록하면 입력한 내용이 시스템에 저장됩니다.
```

업무 의미를 확정할 수 없으면 추측하지 않고 `추가 확인 필요`로 남긴다.

## 4. 프로젝트 업무 용어 사용

프로젝트/고객 용어집이 있으면 다음을 우선 확인한다.

```text
br-input/glossary.csv
```

예시:

```text
sdlc/templates/br-intake/glossary.example.csv
```

기본 컬럼:

```text
term,meaning,alias_or_abbreviation,scope,note
```

고객문서에서는 `term`을 표준 표현으로 우선 사용하고, alias/약어는 원본 탐색과 이해에 활용한다. 용어집만 보고 새로운 업무규칙을 만들지는 않는다.

## 5. A01 — 요구·업무·기능 합의

Requirement Intake 또는 `rq-add` 후 현재 확인된 내용만으로 먼저 만들 수 있다.

```bash
python sdlc/scripts/harness.py customer-view \
  --target RQ-001 \
  --type solution_agreement
```

기본 출력:

```text
docs/20_고객/RQ-001/A01_요구_업무_기능_합의서.md
```

초기에는 미확정 사항이 많고 내용이 간결할 수 있다. 이것은 오류가 아니다.

## 6. A02 — 영향·개발범위 공유

Source/영향/개발범위가 `/work`에서 확인된 뒤 생성할수록 정확하다.

```bash
python sdlc/scripts/harness.py customer-view \
  --target RQ-001 \
  --type delivery_scope
```

기본 출력:

```text
docs/20_고객/RQ-001/A02_영향_개발범위_공유서.md
```

Engineering 문서에 Java Method/Table/Query가 있더라도 고객 본문에서는 `어떤 업무 기능이 어떻게 영향을 받는지` 중심으로 설명한다.

## 7. A03 — 테스트·인수·운영 결과

테스트·검증·운영 인수 근거가 생긴 뒤 생성한다.

```bash
python sdlc/scripts/harness.py customer-view \
  --target RQ-001 \
  --type acceptance_handover
```

기본 출력:

```text
docs/20_고객/RQ-001/A03_테스트_인수_운영_결과서.md
```

테스트 도구나 내부 코드보다 `무엇을 확인했고 결과가 어땠는지`, `고객이 어떤 기준으로 인수하면 되는지`를 우선한다.

## 8. 고객문서 최신화

`/customer-view refresh RQ-001`은 먼저 현재 생성 문서 상태를 확인하고 안전하게 최신화하는 사용법이다.

저수준 상태 조회는 다음 명령으로도 가능하다.

```bash
python sdlc/scripts/harness.py projection status --target RQ-001
```

기본 판단:

```text
문서 없음
→ 생성

현재 기준과 다름
→ 일반 생성본이면 재생성

현재 기준과 같음
→ 기존 문서 사용

사람 검토 대기
→ 현재 문서를 보여주고 검토 대기임을 알림

사람이 직접 수정한 정식 문서
→ 자동 덮어쓰기 금지

최종 검토된 정식 문서
→ 자동 덮어쓰기 금지
→ 현재 기준이 바뀌었으면 별도 미리보기로 차이를 확인하고 다시 검토
```

파일이 존재한다는 이유만으로 최신이라고 판단하지 않는다.

## 9. 고객 검토 결과 기록

고객이나 업무담당자가 현재 문서를 검토하고 승인했다면 생성 문서의 검토상태를 명시적으로 기록할 수 있다.

일반 검토 승인:

```bash
python sdlc/scripts/harness.py projection review \
  --target RQ-001 \
  --artifact-id solution_agreement \
  --reviewer "고객담당자" \
  --accept
```

고객과 최종 문구까지 합의해 이후 자동 덮어쓰기를 막고 싶다면 `--final-review`를 함께 사용한다.

```bash
python sdlc/scripts/harness.py projection review \
  --target RQ-001 \
  --artifact-id solution_agreement \
  --reviewer "고객담당자" \
  --accept \
  --final-review
```

이후 기준 정보가 바뀌더라도 기존 최종 문구는 자동 덮어쓰지 않는다. 새 내용을 비교해야 하면 `--out`으로 별도 미리보기를 만든 뒤 다시 검토한다.

검토 과정에서 단순 표현 수정이 아니라 실제 업무정책 변경 요청이 나온 경우에는 문서만 고치지 않는다.

```bash
python sdlc/scripts/harness.py projection review \
  --target RQ-001 \
  --artifact-id solution_agreement \
  --reviewer "고객담당자" \
  --business-policy-edit "승인 완료 후에는 관리자만 수정할 수 있도록 변경"
```

이 명령은 변경 요청을 기록할 뿐 업무 기준을 자동 수정하지 않는다. 실제 반영은 `/change`로 진행한다.

## 10. Engineering 문서를 추가 근거로 사용할 때

이미 검증된 Engineering 문서를 추가 입력할 수 있다.

기본 `ENGINEERING_SDD_COMPACT` 예:

```bash
python sdlc/scripts/harness.py customer-view \
  --target RQ-001 \
  --type delivery_scope \
  --input docs/10_engineering/RQ-001/00_work-map.md \
  --input docs/10_engineering/RQ-001/specs/RQ-001.md
```

HRIS Custom Profile처럼 프로젝트가 별도 2종 문서를 사용하는 경우에는 해당 Project Profile의 실제 출력 파일을 입력한다.

```text
예: 01_업무정의서.md / 02_작업지시서.md
```

추가 입력 파일 전체를 고객문서에 그대로 복사하지 않는다. Customer Profile과 고객문서 계약에서 허용하는 의미만 사용한다.

## 11. 현재 Source/Test까지 반영하고 싶을 때

다음 요청은 고객문서 생성만으로 끝내지 않는다.

```text
현재 소스까지 반영해서 고객문서 최신화해줘.
방금 개발한 내용과 테스트 결과까지 넣어서 A03 갱신해줘.
```

먼저 실제 근거가 최신인지 확인한다.

```text
Source/DB/Program 현행 재조사 필요 → /work
업무 요구/정책/범위 자체 변경       → /change
이미 검증된 근거 존재              → customer-view 입력으로 사용
```

고객문서 생성 과정에서 Source 사실을 추측하지 않는다.

## 12. 일회성 미리보기 경로

Profile의 정식 고객문서 경로를 건드리지 않고 별도 비교 파일을 만들고 싶다면 `--out`을 사용한다.

```bash
python sdlc/scripts/harness.py customer-view \
  --target RQ-001 \
  --type solution_agreement \
  --out docs/20_고객/RQ-001/미리보기_A01.md
```

공식 Harness에서 `--out`이 정식 Profile 경로와 다르면 **별도 미리보기 Lifecycle로 기록**한다. 따라서 기존 정식 A01의 검토상태나 추적 경로를 미리보기 파일이 덮어쓰지 않는다.

최종 검토된 정식 문서가 있어 기본 경로 재생성이 차단된 경우에도 `--out` 미리보기로 현재 기준의 초안을 별도로 만들어 차이를 검토할 수 있다.

실제 고객에게 미리보기를 공유한다면 동일한 자연어·근거 검토를 거친다.

## 13. 다른 Customer Profile을 시험할 때

프로젝트 기본값을 바꾸지 않고 특정 Profile을 한 번 시험할 수 있다.

```bash
python sdlc/scripts/harness.py customer-view \
  --target RQ-001 \
  --type solution_agreement \
  --tailoring-profile CUSTOMER_STANDARD_3
```

실제 프로젝트 기본값은 `.sdlc/project.yaml`의 `documents.customer.profile`이다.

## 14. 고객문서 수정 요청

```text
A01의 업무규칙을 "승인 후에만 수정 가능"으로 바꿔줘.
```

실제 업무정책 변경이면 `/change`로 기준 정보를 먼저 변경한다.

```text
A01에서 "신청"이라는 표현을 "요청"으로 통일해줘.
```

업무 의미가 변하지 않는 표현 변경이면 고객문서 표현만 수정할 수 있다.

고객문서를 사람이 직접 수정했다고 업무 기준이 자동 변경되지는 않는다. 사람이 수정한 정식 문서는 공식 Customer 생성 명령도 자동 덮어쓰지 않는다.

## 15. 가장 간단한 운영 순서

```text
intake 또는 rq-add
→ A01 작성/미리보기
→ /work 또는 /change
→ /customer-view refresh
→ 개발·테스트
→ A03까지 최신화
→ 고객 검토
→ projection review로 검토 결과 기록
→ 필요 시 최종 검토 문구 보호
```
