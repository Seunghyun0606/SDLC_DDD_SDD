# 고객문서 작성·미리보기·현행화 가이드

## 1. 목적

현재까지 확보된 요구사항·업무 기준 정보·설계/개발/테스트 근거를 이용해 고객용 문서를 미리 생성하고, 프로젝트 진행 중 필요할 때 계속 현행화해서 보는 방법을 설명한다.

고객문서 생성은 업무 기준 정보를 새로 확정하는 작업이 아니다. **현재 확보된 내용으로 고객용 보기 문서를 생성**하며, 없는 사실을 임의로 채우지 않는다.

Cursor에서는 `/customer-view` Skill을 사용할 수 있고, 다른 Agent는 `sdlc/agent/skills/customer-view/SKILL.md`의 같은 규칙을 따른다.

## 2. 기본 Customer Profile

기본 `CUSTOMER_STANDARD_3`는 다음 3종이다.

```text
solution_agreement
→ A01_요구_업무_기능_합의서.md

delivery_scope
→ A02_영향_개발범위_공유서.md

acceptance_handover
→ A03_테스트_인수_운영_결과서.md
```

기본 출력 위치:

```text
docs/20_고객/<RQ>/
```

Custom Customer Profile을 사용하는 프로젝트에서는 3종으로 고정하지 않는다. Profile의 실제 `artifacts`가 1/5/8/13/N종이면 그 구성을 따른다.

## 3. 가장 쉬운 방법 — Skill에 요청

다음처럼 자연어로 요청하면 된다.

```text
RQ-001 고객문서 만들어줘.
RQ-001 고객문서 최신화해줘.
지금 상태 기준으로 고객문서 다시 보여줘.
A01 다시 만들어줘.
A02 영향범위 문서 최신화해줘.
A03 테스트/인수 문서 만들어줘.
고객문서가 최신인지 확인해줘.
```

Cursor에서는:

```text
/customer-view RQ-001
/customer-view refresh RQ-001
/customer-view status RQ-001
```

Skill은 먼저 Customer Profile과 Projection Lifecycle을 확인한 뒤 필요한 문서만 생성/현행화한다.

## 4. 요구사항을 받은 직후 A01 미리보기

Requirement Intake 후 RQ가 만들어졌다면 다음처럼 현재 요구/업무 내용을 고객문서로 미리 볼 수 있다.

```bash
python sdlc/scripts/harness.py customer-view \
  --target RQ-001 \
  --type solution_agreement
```

기본 출력:

```text
docs/20_고객/RQ-001/A01_요구_업무_기능_합의서.md
```

Intake 직후에는 아직 설계가 진행되지 않았으므로 내용이 간결하거나 미확정 사항이 많을 수 있다. 이것은 오류가 아니다.

## 5. 영향/개발범위 문서 미리보기

Source/영향/개발범위가 `/work`에서 보강된 뒤 다음 문서를 생성한다.

```bash
python sdlc/scripts/harness.py customer-view \
  --target RQ-001 \
  --type delivery_scope
```

기본 출력:

```text
docs/20_고객/RQ-001/A02_영향_개발범위_공유서.md
```

## 6. 테스트/인수/운영 문서 미리보기

테스트·검증·운영 인수 근거가 생긴 뒤 다음처럼 생성한다.

```bash
python sdlc/scripts/harness.py customer-view \
  --target RQ-001 \
  --type acceptance_handover
```

기본 출력:

```text
docs/20_고객/RQ-001/A03_테스트_인수_운영_결과서.md
```

## 7. 계속 현행화할 때의 기본 Flow

고객문서를 최신화해 달라는 요청이 들어오면 Skill은 먼저 다음 상태를 확인한다.

```bash
python sdlc/scripts/harness.py projection status --target RQ-001
```

기본 판단 흐름:

```text
고객문서 최신화 요청
→ Customer Profile 확인
→ Profile artifacts 확인
→ projection status 확인
→ 현재 Canonical / 검증된 설계·Source·Test 근거 확인
→ 필요한 문서만 재생성
→ projection status 재확인
→ 최신 / 검토 대기 / 재검토 필요 상태 보고
```

상태별 기본 처리:

- 문서 없음: 생성
- `STALE_VIEW`: 일반 초안이면 재생성 가능
- `CURRENT`: 단순 조회면 기존 문서를 그대로 보여줌
- `PENDING_REVIEW`: 현재 문서를 보여주고 검토 대기임을 알림
- `MANUAL_EDIT_DETECTED`: 자동 덮어쓰기 금지
- `FINAL_REVIEW` 후 기준 정보 변경: 기존 사람 문구 보존, 재검토 필요

## 8. Engineering 문서를 추가 근거로 사용하고 싶을 때

`customer-view`는 현재 RQ의 고객에게 보여도 되는 업무 기준 정보를 기본 입력으로 사용한다. 필요한 경우 이미 생성된 Engineering/Semantic 문서를 추가 입력할 수 있다.

예:

```bash
python sdlc/scripts/harness.py customer-view \
  --target RQ-001 \
  --type delivery_scope \
  --input docs/10_engineering/RQ-001/01_업무정의서.md \
  --input docs/10_engineering/RQ-001/02_작업지시서.md
```

추가 입력이 있다고 해서 문서 내용 전체가 고객에게 그대로 복사되는 것은 아니다. Customer Profile과 고객문서 계약이 허용하는 내용만 조립한다.

Skill은 전체 Engineering 폴더를 무조건 입력하지 않고 Target과 실제 관련된 현재 근거만 선택한다.

## 9. 현재 Source/Test까지 반영하고 싶을 때

다음 요청은 고객문서 생성만으로 처리하지 않는다.

```text
현재 소스까지 반영해서 고객문서 최신화해줘.
방금 개발한 내용과 테스트 결과까지 넣어서 A03 갱신해줘.
```

이 경우 Skill은 먼저 실제 Source/Test 근거가 최신인지 확인한다.

- Source/DB/Program 현행을 다시 조사해야 함 → `/work`
- Requirement/Business Rule/Scope/TO-BE 의미 변경 → `/change`
- 이미 검증된 Engineering/Test 근거가 있음 → 해당 파일을 `--input`으로 사용

고객문서 생성 과정에서 Source 사실을 추측하지 않는다.

## 10. 출력 위치를 임시로 바꾸고 싶을 때

Profile 기본 경로를 바꾸지 않고 일회성 미리보기 파일만 만들고 싶다면 `--out`을 사용한다.

```bash
python sdlc/scripts/harness.py customer-view \
  --target RQ-001 \
  --type solution_agreement \
  --out docs/20_고객/RQ-001/미리보기_A01.md
```

## 11. 다른 Customer Profile을 한 번만 시험하고 싶을 때

프로젝트 기본 설정을 바꾸지 않고 특정 Profile을 시험하려면:

```bash
python sdlc/scripts/harness.py customer-view \
  --target RQ-001 \
  --type solution_agreement \
  --tailoring-profile CUSTOMER_STANDARD_3
```

실제 프로젝트의 기본 Profile은 `.sdlc/project.yaml`의 `documents.customer.profile`이 기준이다.

## 12. FINAL_REVIEW 문서는 왜 자동으로 다시 만들지 않는가

최종 제출 직전에 사람이 표현을 직접 다듬은 고객문서는 일반 Agent 초안과 다르다.

```text
FINAL_REVIEW + 현재 기준 정보 동일
→ 기존 문서 유지
→ 현재 문서로 보여줌

FINAL_REVIEW + 이후 기준 정보 변경
→ 기존 문서 재확인 필요
→ 사람 수정 문구 보존
→ 자동 덮어쓰기 금지
→ /change 또는 /work 반영 여부 확인
→ 다시 검토
```

따라서 `/customer-view refresh`도 FINAL_REVIEW나 수동수정 감지 문서를 무조건 덮어쓰지 않는다.

## 13. 고객문서의 내용 수정 요청을 받았을 때

고객이나 사용자가 고객문서의 특정 내용을 바꿔 달라고 하면 의미를 먼저 구분한다.

```text
A01의 업무규칙을 "승인 후에만 수정 가능"으로 바꿔줘.
```

실제 정책 변경이면 `/change`로 업무 기준 정보를 먼저 갱신한다.

```text
A01에서 "신청"이라는 표현을 "요청"으로 통일해줘.
```

업무 의미가 변하지 않는 표현 변경이면 Projection-only 수정으로 다룰 수 있다.

고객문서를 사람이 수정했다고 해서 업무 기준 정보가 자동 변경되지는 않는다.

## 14. 주의사항

- `customer-view`는 `/work`나 `/change`를 대신하지 않는다.
- 업무규칙/범위/TO-BE가 바뀌면 `/change`로 기준 정보부터 갱신한다.
- Source/DB/프로그램 현행을 다시 반영하려면 `/work`를 먼저 수행한다.
- 고객문서를 사람이 수정했다고 해서 업무 기준 정보가 자동 변경되지 않는다.
- 최종 검토 후 기준 정보가 변경되면 기존 고객문서는 다시 확인이 필요한 상태가 될 수 있다.
- 고객문서가 존재한다는 이유만으로 최신이라고 판단하지 않고 Projection 상태를 확인한다.

## 15. 가장 간단한 사용 순서

```text
intake
→ A01 미리보기
→ /work 또는 /change
→ /customer-view refresh
→ 개발·테스트
→ /customer-view refresh
→ 고객 검토/인수
```

고객문서는 필요할 때 여러 번 다시 생성할 수 있다. 단 최종 검토에서 사람이 직접 다듬은 문구가 있는 경우에는 자동 덮어쓰지 않고 재검토 경계를 따른다.
