# 요구사항 인입 완성 예시

이 문서는 사용자가 작성해야 하는 빈 Template이 아니라, `harness.py intake`가 어떤 결과를 만드는지 보여주는 **완성된 예시**다.

## 제공 자료

`requirements.xlsx`의 요구사항 행이 다음과 같다고 가정한다.

| Level1 | Level2 | 요구사항 ID | 요구사항명 | 요구사항 |
|---|---|---|---|---|
| 휴가관리 | 신청 | REQ-LEAVE-001 | 휴가 신청 개선 | 직원이 휴가를 신청한다 |
| 휴가관리 | 신청 | REQ-LEAVE-002 | 휴가 신청 개선 | 잔여 휴가일수를 확인한다 |

사용자는 이 표를 Harness Template으로 다시 옮겨 적지 않는다. 원본 XLSX를 그대로 제공한다.

## 실행

```bash
python sdlc/scripts/harness.py intake requirements.xlsx
```

## Machine Runtime 결과 예시

Canonical에는 다음과 같은 **후보**가 등록된다.

- `RQ-001`
  - 이름: 휴가 신청 개선
  - 업무영역: 휴가관리 / 신청
  - 원본 외부 ID: REQ-LEAVE-001, REQ-LEAVE-002
  - 현재 문제: OPEN
  - 원하는 결과: OPEN
  - 업무 규칙: OPEN
  - 상태: CANDIDATE
- `FR-001`: 직원이 휴가를 신청한다 — CANDIDATE
- `FR-002`: 잔여 휴가일수를 확인한다 — CANDIDATE
- 관계: `RQ-001 --HAS_FR_CANDIDATE--> FR-001, FR-002`

Source 행의 Sheet/Row와 Source Hash도 Provenance로 보존된다. 이 관계는 원본 묶음에 근거한 후보 연결이며 승인된 업무 분해를 의미하지 않는다.

## 사람에게 보이는 결과 예시

사람은 다음만 확인하면 된다.

- 같은 이름으로 묶인 두 행을 하나의 RQ로 보는 것이 맞는가?
- 휴가 신청 시 필요한 승인 정책·대상 범위·예외 규칙은 무엇인가?
- 원문만으로 확인할 수 없는 기대 결과를 누가 확정할 것인가?

사람이 `requirement.md`의 수십 개 placeholder를 채우는 것이 기본 절차가 아니다.

## Agent가 이어서 하는 일

Intake 결과가 반환한 실제 Target을 그대로 사용한다.

```bash
python sdlc/scripts/harness.py work --target RQ-001
```

Provider가 아직 연결되지 않았다면 다음처럼 계획만 확인한다.

```bash
python sdlc/scripts/harness.py work --target RQ-001 --plan-only
```

`RQ-001`은 Canonical에 존재하므로 `/work`는 DECOMPOSE를 선택하고, Source에서 확보한 RQ/FR 후보를 Context로 받아 Requirement 초안을 만든다. 업무 정책·범위·승인처럼 근거가 없는 값은 OPEN으로 유지한다.

## 산출물 분리

- 사용자 확인 문서: `docs/00_관리/요구사항_인입결과.md`
- Machine intake artifact: `sdlc/runtime/intake/requirements-import.json`
- Canonical target store: `sdlc/canonical/store.json`
- 다음 Agent 산출물: `/work`가 생성하는 `requirement.md`

사용자는 Machine JSON을 직접 편집할 필요가 없다.
