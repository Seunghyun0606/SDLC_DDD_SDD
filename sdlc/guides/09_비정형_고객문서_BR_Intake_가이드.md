# 비정형 고객문서 BR Intake 가이드

## 결론
고객에게 기존 문서를 특정 BR Template로 다시 작성하도록 요구하지 않는다. **원본 문서는 원형 그대로 받고**, 최소한의 문서 등록표(Manifest)를 함께 받으며, Harness가 원본 근거를 보존한 `BR 후보`로 정규화한다.

## 권장 제공 구조
```text
br-input/
├─ originals/                 # 고객 원본. 이름 변경/편집/병합 금지
│  ├─ 규정.pdf
│  ├─ 운영매뉴얼.docx
│  ├─ 요구목록.xlsx
│  ├─ 회의자료.pptx
│  └─ 회의록.docx
├─ manifest.yaml              # 최소 문서 등록표
├─ context.md                 # 선택: 프로젝트 배경, 범위, 시스템명
├─ glossary.csv               # 선택: 고객 용어/약어
└─ decisions/                 # 선택: 승인 메일, 결정 회의록, 변경 이력
```

## 최소 제공 항목 — 반드시 필요한 것
각 문서마다 다음 두 가지만 있어도 Intake를 시작할 수 있다.
1. `document_id`: 문서를 안정적으로 참조할 ID
2. `path`: 원본 파일 위치

원본 파일 자체는 변경하지 않는다. 파일 해시는 Harness가 계산하거나 보존한다.

## 권장 제공 항목 — 정확도를 높이는 것
- 문서 제목
- 문서 종류: 규정/계약/매뉴얼/절차/회의록/메일/티켓/엑셀/슬라이드 등
- 문서 권위: 승인본/공식/참고/초안/모름
- 현재 유효 여부
- 작성/관리 부서 또는 담당자
- 적용 시작일
- 적용 업무 범위
- 관련 프로세스/시스템
- 위치 표기 방식: 페이지, Sheet+Cell, Slide, 문단, Heading 등

모르는 값은 비워두거나 `UNKNOWN`으로 둔다. Agent가 추정값을 사실로 승격하지 않는다.

## 선택 제공 항목
- 고객 용어집/약어집
- 문서 간 우선순위
- 폐기/대체 관계
- 승인·결정 이력
- 이미 알고 있는 문서 간 충돌
- 관련 RQ/FR/시스템 ID 힌트

## BR 정규화 결과
한 문장에서 다음을 가능한 범위에서 분리한다.
- 적용 조건
- 수행 주체
- 해야 할 행동 또는 판단
- 기대 결과
- 예외
- 적용 기간
- 원본 문서와 정확한 위치
- 문서 권위/상태
- 신뢰도
- 관련 RQ/FR/Process/System

원문은 `original_text`로 보존하고 자연어 정리본은 `normalized_statement`로 별도 저장한다.

## 충돌 처리
두 문서가 서로 다른 규칙을 말해도 자동으로 최신 문서나 높은 권위 문서를 정답으로 선택하지 않는다. `BR_CONFLICT`로 묶고 고객/업무 담당자 확인 질문을 만든다.

## 파일 형식
PDF, DOCX, XLSX, PPTX, Markdown, TXT, CSV 등은 원본 그대로 받을 수 있다. 스캔 이미지 등 텍스트를 신뢰성 있게 추출할 수 없는 자료는 `EXTRACTION_REQUIRED`로 남기고 내용을 발명하지 않는다.
