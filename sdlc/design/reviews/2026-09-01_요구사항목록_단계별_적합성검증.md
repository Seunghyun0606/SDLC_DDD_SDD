# 요구사항목록 Sample 단계별 적합성 검증

> 대상 입력: 첨부 `요구사항목록.xlsx`
> 기준 Baseline: `AI_SDLC_Harness_Full_Design_v1.5.1.md`
> 목적: 실제 기존 프로젝트의 요구사항 목록이 Harness의 INTAKE→PROMOTION 흐름에 들어왔을 때 각 단계 요건에 맞게 진행 가능한지 검증
> 판정 원칙: Excel에 없는 의미를 임의로 보완하지 않는다. Source/Analyzer/Test가 없으면 해당 근거가 필요한 Stage는 확정하지 않는다.

---

# 1. Quick Result

## 결론: `CONDITIONALLY USABLE AS LEGACY REQUIREMENT INVENTORY`

첨부 Excel은 Harness 입력으로 **사용 가능하지만, 142행을 142개의 독립 RQ로 바로 승격해서는 안 된다.**

핵심 이유:

1. 총 142개 행은 모두 `근태관리`이며 Level2는 10종이다.
2. `요구사항명`은 22종뿐이며 동일 상위명 아래 CRUD/조회/송신/Batch 세부 기능이 반복된다.
3. 예: `10분단위 근무계획 개선 근태마감 반영을 구현`은 39행, `근태현황/통계`는 22행, `근무집계`는 23행이다.
4. 따라서 현재 Excel은 Business Requirement 원장이라기보다 **상위 요구사항 후보 + 세부 기능 목록**에 가깝다.
5. 일정/담당자 필드는 존재하지만 시작일/종료일/담당자는 142건 모두 공란이다. v1.5.1의 Optional PM 정책과는 충돌하지 않는다.

권장 Import 형태:

```text
Legacy Excel Row
→ 원본 보존
→ Requirement Group Candidate
→ FR Candidate
→ Human Review
→ RQ/FR Publish
```

행을 바로 RQ로 만들지 않고 원본 ID를 보존한 채 Normalization Candidate를 만든다.

# 3. Stage별 검증

| Stage | Excel만으로 진행 | 허용 가능한 결과 상태 | 판정 | 이유 / 필요한 보완 |
|---|---|---|---|---|
| INTAKE | 부분 가능 | `CANDIDATE / WARNING` | WEAK | 이름과 세부기능은 있으나 v1.5.1 최소 입력인 `현재 문제 또는 요청내용`, `원하는 결과`가 명시되지 않음 |
| DECOMPOSE | 조건부 가능 | `DRAFT` | WEAK | 22개 상위명과 142개 세부행으로 RQ/FR 후보화 가능. 확정하려면 Grouping Review 필요 |
| CLARIFY | 가능 | `OPEN / ALERT / ASM` | PASS | Excel의 부족 정보를 기반으로 질문 생성 가능. 단 BR을 CONFIRMED로 만들 근거는 없음 |
| PROCESS | 초안만 가능 | `DRAFT / CRITICAL` | WEAK | CRUD/조회/송신 목록만으로 Actor, Trigger, State, AS-IS/TO-BE 확정 불가 |
| DISCOVERY | 불가 | `NOT_STARTED` | FAIL | Source Repository/Static Analyzer 결과가 첨부되지 않아 Evidence 기반 탐색 불가 |
| IMPACT | Candidate 일부만 가능 | `CANDIDATE` | FAIL | Level2/명칭 기반 Business 후보는 만들 수 있으나 Technical/Functional Impact Recall 검증 불가 |
| DESIGN | 초안만 가능 | `DRAFT / WARNING` | WEAK | Transaction, Authorization, Validation, Exception, Interface Contract, NFR 부족 |
| PROGRAM | 불가 | `NOT_STARTED` | FAIL | PGM/ART/SYMBOL 매핑 근거가 없음 |
| DEVELOPMENT | Source Write 불가 | `DEFERRED_TARGET_DECISION / EXECUTION_GUARDED` | FAIL | Target Write Proof가 없으므로 소스 수정은 안전하지 않음 |
| TEST | 후보 생성 가능 | `DRAFT` | WEAK | 정상 흐름 TC 후보는 만들 수 있으나 기대값, 경계값, 예외, Transaction, Batch/Interface 조건 부족 |
| VERIFY | 불가 | `NOT_STARTED` | FAIL | Source 변경 및 Test Result가 없음 |
| KNOWLEDGE PROMOTION | K3만 가능 | `HISTORICAL EVIDENCE` | WEAK | 요구사항 목록은 Confirmed Business Rule이나 Verified Technical Knowledge가 아님 |
| PM/TASK | 부분 가능 | `ROUGH` | PASS | 담당/일정은 Optional이므로 공란 허용. 단 아직 RQ/FR/PGM/TASK 구조가 확정되지 않음 |

## 핵심 판정

Excel만으로 Harness 전체 SDLC가 완료되는 구조가 되어서는 안 된다.

```text
Excel
→ INTAKE Candidate
→ Decompose Candidate
→ Clarification
→ Source/Evidence 연결
→ Process/Impact/Design
→ Program/Task
→ Development/Test/Verify
```

즉 첨부 Excel은 **시작점으로 충분하지만 완료 근거로는 부족하다.**

# 4. 실제 Sample Flow 검증

## Sample A — `REQ_TM_FL001~003`

상위명:

`탄력근로제 개선 최초근무계획 자동 설정하는 기능`

세부 기능:

- 근무계획 저장
- 근무계획 조회
- 기본 근무스케줄에 따라 근무계획 생성 자동 저장

### 가능한 진행

```text
INTAKE Candidate
→ RQ 후보 1건
→ FR 후보 3건
→ 질문 생성
```

### 반드시 질문해야 하는 것

- 최초 근무계획 생성 Trigger는 무엇인가?
- 누구에게 적용되는가?
- 기존 근무계획이 있으면 overwrite하는가?
- 자동 생성 범위는 일/주/월 중 무엇인가?
- 실패 시 부분 저장을 허용하는가?
- 저장과 조회의 권한 조건은 무엇인가?

### 판정

`DECOMPOSE`까지는 현실적으로 가능. Process/Design 확정에는 추가 Truth와 Source가 필요하다.

---

## Sample B — `REQ_TM_FL014~021`

상위명:

`탄력근로제 개선 고과제/연봉제 예외사항 요청하는 기능`

세부 기능에는 승인요청 등록/삭제/조회, 전자결재 송신/수신, 승인 후처리 집계 저장, 승인요청 취소가 포함된다.

### 검증 포인트

이 Requirement는 단순 CRUD가 아니라 다음이 숨어 있을 가능성이 높다.

```text
요청
→ 전자결재 송신
→ 승인/반려/취소
→ 수신
→ 후처리 집계
```

Excel에는 State Transition, 결재 실패, 중복 수신, 취소 가능 시점, Transaction Boundary가 없다.

### 판정

- INTAKE/DECOMPOSE: 가능
- CLARIFY: 질문 생성 가능
- PROCESS/DESIGN: DRAFT only
- PROGRAM 이후: Source Evidence 없이는 진행 불가

이 유형은 Context Underfitting보다 **Process Underfitting** 위험이 먼저 발생한다.

## Sample C — `REQ_TM_TE016~054`

상위명:

`10분단위 근무계획 개선 근태마감 반영을 구현`

세부 기능 수: 39

일마감, 월마감, 전자결재, 강제마감, 전사마감, 선택적 근로마감 등이 한 상위명 아래 포함된다.

### 위험

39행을 하나의 RQ로 묶으면 RQ가 지나치게 크고, 39행을 각각 RQ로 만들면 Canonical/PM Task가 과도하게 분해된다.

따라서 최소한 다음 중간 계층이 필요할 수 있다.

```text
RQ: 10분단위 근무계획 개선
  └─ FR Group: 근태마감
       ├─ 일마감
       ├─ 월마감
       ├─ 전자결재
       └─ 선택적근로마감
```

현재 RQ→FR→FTR 구조로 표현 가능하지만 Import 시 Grouping Algorithm이 필요하다.

### 판정

현재 Canonical Entity를 새로 추가할 필요는 없다. 하지만 **Legacy Requirement Normalizer**가 없으면 실제 도입 시 RQ/FR granularity가 사람마다 달라진다.

## Sample D — `REQ_TM_TE077~099`

상위명:

`10분단위 근무계획 개선 근무집계 반영을 구현`

세부 기능 수: 23

Batch, 45hr/52hr 예상 초과 조회, 안내메일, 회사/고용형태별 일근무집계가 혼재한다.

### 위험

이 영역은 Excel만 보고 Program Impact를 추정하면 특히 위험하다.

- Batch Scheduler
- 파일 연계
- 공통 Procedure
- 회사별 분기
- 급여/수당 후행 Consumer
- 운영 시간대

가 Source/Runtime에 숨어 있을 수 있다.

### 판정

`DISCOVERY/IMPACT`는 반드시 Static Analysis + Batch/Runtime 보강이 필요하며, Excel 명칭만으로 `VERIFY_ONLY`/`MODIFY`를 정해서는 안 된다.

# 6. 이번 Sample이 드러낸 실제 Architecture Gap

## GAP-REQ-IMPORT-01 — Legacy Requirement Intake Normalization

### Gap
기존 프로젝트의 요구사항 Excel이 Harness Canonical의 RQ granularity와 다를 때 어떻게 정규화하는지 계약이 없다.

### 왜 기존 설계로 부족한가
Existing Asset Bootstrap은 Source/Guide 중심이고, 기존 요구사항 목록의 `row = RQ인지 / FR인지 / Task인지`를 결정하는 Import 계약은 명시되지 않았다.

### Minimal Fix

```text
Raw Requirement Source
→ Preserve Legacy ID/Row
→ Group Candidate
→ RQ/FR Candidate
→ Human Review
→ Publish
```

필수 Provenance:

- source_file
- source_sheet
- source_row
- legacy_requirement_id
- import_rule_version
- normalization_confidence

### PoC 전 필요
`YES`

# 7. MD↔Excel 검증 결과

이번 Review에서는 Sample 데이터로 다음 Workbook을 별도 생성했다.

- `원본요구사항`: 142행 원본을 단일 한글 Header 형태로 보존

이로써 **한글 컬럼 기반 Excel View와 Normalized Candidate Schema가 표현 가능한 것**은 확인했다.

그러나 다음은 아직 구현 검증되지 않았다.

- MD 수정 → Canonical Import → Excel 재생성
- Excel 수정 → Canonical Import → MD 재생성
- revision 충돌
- `SYNC_CONFLICT`
- Binary Excel round-trip에서 사용자 formatting/추가 컬럼 보존

따라서 현재 판정은:

`SCHEMA/UX FEASIBLE, BIDIRECTIONAL CONVERTER NOT YET VERIFIED`

# 10. DECISION_REQUIRED

## Question
기존 요구사항 Excel의 한 행을 Canonical에서 기본적으로 무엇으로 취급할 것인가?

### Option A — Row = RQ

Pros
- Import가 단순함
- 기존 ID 1:1 보존 쉬움

Cons
- 현재 Sample에서는 142개 RQ가 생성되어 CRUD 단위 과분해 가능성이 높음
- PM/Knowledge/Trace가 불필요하게 세분화됨

### Option B — `요구사항명` = RQ Candidate, Row = FR Candidate

Pros
- 현재 Sample의 반복 구조와 잘 맞음
- RQ 22개 후보 + FR 142개 후보 형태로 자연스러움

Cons
- 다른 프로젝트 Excel에서는 `요구사항명` 의미가 다를 수 있음
- 자동 Grouping이 잘못될 수 있음

### Option C — Raw Row는 Import Source Entity로만 보존하고 Agent가 RQ/FR Candidate를 제안

Pros
- 기존 데이터 의미를 왜곡하지 않음
- 프로젝트별 다양성에 가장 안전

Cons
- Import 구현과 Review UX가 조금 더 필요

## Red Team Recommendation

`Option C`를 Core로 두고, 현재 Sample용 Overlay에서 `Option B` Grouping Rule을 제안한다.

즉 Core는 행 의미를 고정하지 않고, Project Mapping이 RQ/FR 후보를 만든다.

## Why final choice still belongs to user

기존 프로젝트마다 요구사항 목록의 행 의미가 다르므로 Core에서 일괄 `Row = RQ` 또는 `Row = FR`로 고정하면 다른 프로젝트에 적용할 때 데이터 의미를 훼손할 수 있다.

# 11. Final Verdict

첨부 요구사항목록은 Harness Pilot에 사용할 수 있다.

단 다음처럼 사용해야 한다.

```text
요구사항목록.xlsx
→ Legacy Source Import
→ 22개 RQ Group Candidate + 142개 FR Candidate 제안
→ 사람 Review
→ 질문/Assumption
→ Source/Analyzer 연결
→ Impact/Design/Program
→ Development/Test/Verify
```

현재 v1.5.1은 사용자 UX/작업목록/한글 컬럼/Non-blocking/PM 측면에서는 Sample을 수용할 기반이 있다.

가장 큰 추가 Gap은 **Legacy Requirement Intake Normalization**이다.

이 Gap을 보완하지 않고 142행을 그대로 RQ로 받아들이면, Harness는 실제 프로젝트를 돕기 전에 Requirement Granularity부터 왜곡할 가능성이 높다.
