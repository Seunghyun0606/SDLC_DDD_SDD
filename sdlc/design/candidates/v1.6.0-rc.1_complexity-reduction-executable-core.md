# v1.6.0-rc.1 Complexity Reduction / Executable Core

## 목적
v1.5.9까지 추가된 기능을 더 확장하기 전에 실제 프로젝트 사용성을 기준으로 문서·상태·설정 복잡도를 줄인다.

핵심 원칙은 다음과 같다.

1. 같은 업무정보는 한 번만 작성한다.
2. 사람에게 필요한 정보와 Machine metadata를 분리한다.
3. Requirement 원문과 분석결과는 하나의 활성 Artifact에서 관리한다.
4. Functional Design은 업무/기능 의미의 기준 문서다.
5. Program Spec은 Functional Design을 반복하지 않고 실제 구현 Target과 구현 차이만 추가한다.
6. OPEN은 사람에게는 간단한 진행 상태로 표시하고 세부 분류/근거 코드는 Machine metadata로 유지한다.
7. /setup은 최소 5개 입력으로 시작 가능해야 하며 나머지 Profile은 필요할 때만 고급 설정으로 확장한다.
8. 고객 커뮤니케이션 문서는 Stage별 8개가 아니라 목적별 3개 활성 View로 통합한다.
9. 고객 View는 내부 Markdown/Canonical JSON에서 Projection하며 없는 업무사실을 생성하지 않는다.
10. 기존 RQ/FR/BR/PGM/TASK/AC/TC 및 Evidence 안전 규칙은 유지한다.
11. Brownfield Framework 분석은 Core에 흡수하지 않고 Project Adapter 경계를 유지한다.
12. Source Drift는 Reverse Engineering 전체가 아니라 Drift/Reverse Review Candidate 기능으로 표현한다.
13. 새 Template/Contract 추가보다 기존 구조 축소와 실제 실행 경로 구현을 우선한다.

## 이번 RC 범위

### 1. Requirement / Requirement Analysis 활성 산출물 통합
신규 Workflow에서는 `requirement.md` 하나가 다음을 함께 가진다.
- 원문과 External ID
- 현재 문제/요청
- 업무 목표와 기대 결과
- Scope/Constraint
- 기능 요구사항(FR)
- 업무 규칙(BR) 후보
- 인수 조건(AC)
- OPEN/Trace

`requirement-analysis.md`는 기존 링크 호환을 위한 `DEPRECATED_COMPATIBILITY_VIEW`로 남기며 새 업무정보를 작성하지 않는다. 호환 소비자가 제거되면 파일 삭제를 검토한다.

### 2. Functional Design / Program Spec 책임 분리
Functional Design이 다음의 의미상 Source of Truth를 가진다.
- 6하원칙 업무 시나리오
- AS-IS / TO-BE
- 화면/사용자 동선
- Field 의미와 Validation
- CRUD 의미
- Business Rule / 상태 / 예외
- 논리 Data 요구
- Integration 요구
- Authorization / NFR
- AC 연결

Program Spec은 다음만 추가한다.
- Functional Design 참조 및 적용 범위
- 실제 PGM/Entry Point/Source Symbol
- Field→DTO/API/DB Mapping 차이
- 실제 Query/Table/Column/Mapper
- Transaction/Concurrency/Idempotency
- Integration 구현 Contract
- Error/Security/Observability 구현 방식
- TASK/AC/TC와 실제 Source 변경 대상
- 구현 준비도와 남은 OPEN

Program Spec에서 Functional Design 내용을 다시 풀어 쓰지 않는다.

17개 Program DoR 의미는 유지하되 17개 별도 Section 대신 단일 구현 준비도 표의 17개 행으로 관리한다.

### 3. OPEN 사람 표시 단순화
Machine 상태는 기존 호환성을 위해 유지한다.

사람 표시 상태는 다음 5개로 축소한다.
- 미확정
- 확인중
- 제안
- 확정
- 보류

`decision_domain`, `resolution_method`, `basis_class`, 내부 status code는 기본 사용자 문서에서 직접 입력시키지 않는다. Agent/Script가 가능한 범위에서 계산하고 필요 시 내부 부록에서만 표시한다.

### 4. /setup Fast Path
최초 시작 시 다음만 묻는다.
1. 프로젝트 유형: Greenfield / Brownfield / Hybrid / Auto
2. 요구사항 또는 변경요청 위치
3. Source/Repository 위치(없으면 없음)
4. Build/Test 경로(모르면 자동탐색)
5. 고객용 문서 필요 여부

용어, Authority, Customer Section, BR Intake, Impact Adapter 등은 기본값으로 시작하고 실제 필요가 확인될 때 Advanced Setup에서 변경한다.

### 5. 고객문서 8종 → 3개 활성 View
기존 `customer-document-contract.json`을 확장해 다음 3개만 신규 활성 View로 사용한다.

| 활성 View | 담당 Stage | 목적 |
|---|---|---|
| `solution_agreement` — 요구·업무·기능 합의서 | INTAKE, DECOMPOSE, CLARIFY, PROCESS, DESIGN | 요청, 업무흐름, 주요 기능, 업무규칙, 결정 필요사항 합의 |
| `delivery_scope` — 영향·개발범위 공유서 | DISCOVERY, IMPACT, PROGRAM, DEVELOPMENT | 영향, 개발 범위, 구현 상태와 제약 공유 |
| `acceptance_handover` — 테스트·인수·운영 결과서 | TEST, VERIFY, KNOWLEDGE_PROMOTION | 인수기준, 검증 결과, 미수행 항목, 운영 인수 확인 |

기존 8개 document type ID는 삭제하지 않고 `legacy_document_aliases`로 3개 View에 연결한다. 따라서 기존 호출/링크 호환성을 유지하면서 신규 프로젝트의 고객문서 선택지는 3개로 줄인다.

새로운 Customer Contract를 추가하지 않았다. 기존 `customer-document-contract.json`에 활성 View와 Projection Mapping을 추가했다.

### 6. 내부 Artifact → Customer View Projection Runtime
기존 `render_customer_document.py`는 Heading/placeholder skeleton만 만들었다. 이번 RC에서는 다음 실제 입력을 읽도록 변경했다.
- 내부 Markdown Artifact
- Canonical JSON Bundle
- 위 파일이 포함된 디렉터리

Projection은 Contract에 명시된 `projection_sections`, `base_section_sources`, `catalog_section_sources`를 사용한다.

실행 원칙:
1. 선택한 고객 View가 담당하는 Stage의 내부 Artifact만 사용한다.
2. 최신 Stage 내용을 우선하고 반복 내용은 중복 제거한다.
3. 내부 RQ/FR/BR/PGM/TASK/AC/TC ID, Source Hash, Locator, Confidence는 기본 고객 본문에서 숨긴다.
4. `OPEN`, `CONFIRMED_BUSINESS` 등 내부 상태는 고객용 한국어 표현으로 변환한다.
5. `합의된 내용` 등 근거가 없는 Section은 추정하지 않고 명시적 미확인 문구를 출력한다.
6. 고객 회의에서 바뀐 내용은 고객 문서만 수정하지 않고 내부 Canonical/Artifact에 반영한 뒤 Projection을 다시 수행한다.

즉, Customer View는 별도 Truth Store가 아니라 내부 Artifact의 파생 View다.

## 유지하는 Core
- Human Truth / Existing System Evidence / Proposed Design 분리
- RQ → FR/Scenario → BR → PGM → TASK → AC/TC → Source 추적
- OPEN/가정/충돌을 발명하지 않는 규칙
- Brownfield Project Adapter 경계
- Source Hash 및 Drift 안전장치
- Business Truth 자동 역갱신 금지

## 제거/축소 방향
- Requirement 원문과 분석결과를 두 개의 활성 문서로 나누지 않는다.
- 동일한 6W/Field/CRUD/Rule을 Functional Design과 Program Spec에 중복 작성하지 않는다.
- 17개 Program DoR를 17개 Section으로 만들지 않는다.
- OPEN Workbook에서 10개 이상 Machine column을 사람이 직접 관리하지 않는다.
- /setup 최초 진입에서 모든 Profile을 필수 설정으로 취급하지 않는다.
- 고객용 문서를 Stage별 8개 활성 산출물로 생성하지 않는다.
- 고객문서 생성을 빈 Template 복사 작업으로 남겨두지 않는다.
- 고객용 문서는 내부 Machine state를 기본 노출하지 않는다.

## 후속 RC / Pilot
이번 RC는 복잡도 축소와 Customer Projection의 첫 실행 구현까지 포함한다. 다음 항목은 실제 실행 기반 또는 추가 영향 검토가 필요하므로 별도 검증한다.
- Interview View와 OPEN Workbook 파생 관계의 추가 자동화
- 실제 Greenfield/Brownfield 산출물 묶음 기반 Customer Projection Pilot
- Stage 실행 경로의 실제 Canonical Delta executor
- 저수준 Agent 반복 실행 기반 behavioral validation
- 실제 Java/Spring/MyBatis Project Adapter Pilot
- Source → Program Spec semantic regeneration/diff

## 비호환성 정책
기존 Machine key와 상태값은 당분간 유지한다. 기존 링크를 깨뜨릴 가능성이 있는 파일/Document Type 제거는 즉시 하지 않고 Legacy View/Alias로 먼저 비활성화한다. 실제 사용 데이터의 migration 계획이 확인된 뒤 내부 schema/파일 제거를 검토한다.
