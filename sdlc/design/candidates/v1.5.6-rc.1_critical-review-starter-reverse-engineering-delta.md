# v1.5.6-rc.1 — Critical Review / Mode Starter Kit / Reverse Engineering Delta

## 1. 검토 목적
v1.5.5까지의 설계를 기능 추가 관점이 아니라 실제 SDLC 사용 가능성 관점에서 다시 평가한다.

검토 질문은 다음 6개다.
1. 현재 산출물이 실제 설계/개발/고객 협의에 충분히 효과적인가?
2. 사용자가 쉽게 시작하고 검토할 수 있는가?
3. 상대적으로 저수준의 Agent도 문서 계약만 보고 일관된 산출물/소스를 생성할 수 있는가?
4. Brownfield에서 실제 Source 기반 영향도 분석이 충분한가?
5. Source 변경으로부터 이전 단계 산출물을 역방향 갱신할 수 있는가?
6. 현재 Source에서 Business Rule과 Program Spec을 복원할 수 있는가?

## 2. 종합 판정
| 영역 | 현재 판정 | 성숙도 | 결론 |
|---|---|---:|---|
| 산출물 효과성 | 조건부 충족 | 3.5/5 | Trace/Evidence/Program DoR는 강함. Stage별 내용 계약은 더 구체화 필요 |
| 사용자 사용성 | 조건부 충족 | 3.5/5 | 한글/Customer View는 개선됨. Mode별 시작 가이드가 부족했으며 Starter Kit으로 1차 보완 |
| 저수준 Agent 재현성 | 미충족에 가까운 조건부 | 2.5/5 | Reference가 너무 압축적. 결정적 실행 절차/예시/출력 Schema가 부족 |
| Brownfield 영향 분석 | 미충족 | 2.0/5 | Static Analysis First 원칙은 맞지만 실제 관계 확장/coverage 계약이 부족 |
| Source→이전 산출물 Reverse | 미충족 | 1.5/5 | STALE 처리 개념은 있으나 Source Diff 기반 역방향 파이프라인 없음 |
| Source→Program Spec | 부분 충족 | 3.0/5 | 기술적 AS-IS Program Spec 후보는 가능. Requirement 없는 Program Inventory 모델 필요 |
| Source→Business Rule | 후보 추출만 가능 | 2.0/5 | 코드 조건/검증은 관찰 규칙 후보로 가능. Business Truth 자동 확정은 불가 |

현재 설계를 **완성된 Brownfield/Reverse Engineering Harness로 판정해서는 안 된다.**

## 3. 1번 — 산출물 효과성
### 강점
- 모든 Core Template이 한국어 공통 8단락으로 통일되어 문서 탐색성이 좋다.
- Requirement→FR→PGM→TASK→AC/TC Trace를 유지한다.
- Source Evidence에 Locator/Hash/Confidence/Status를 둔다.
- Program Spec 17-field DoR는 실제 구현 착수 가능성을 점검하기에 유효하다.
- 고객 View가 Canonical에서 파생되므로 내부 설계와 고객 문서의 Truth가 분리되지 않는다.

### 한계
1. 많은 Stage Template의 `업무 흐름`이 공통 예시 수준이라 Stage 자체의 사고 구조를 충분히 안내하지 않는다.
2. `DISCOVERY`와 `IMPACT`가 동일한 `impact-analysis.md`를 공유해 탐색 결과와 영향 판정의 경계가 약하다.
3. Program Spec에 많은 기술 계약이 집중되어 DESIGN/PROCESS 단계가 상대적으로 얕아질 수 있다.
4. 상태 모델, 업무 데이터 사전, Interface Contract, Decision Log 등 복잡 프로젝트에서 자주 필요한 산출물은 Optional Module로 명시되지 않았다.
5. 문서가 많아질 때 어떤 문서를 고객/설계/개발자가 우선 읽어야 하는지 역할별 Review Path가 없다.

### 판정
**조건부 충족.** 기본형 프로젝트에는 유효하지만 복잡한 개발 프로젝트를 위한 Stage-specific content contract와 Optional Artifact Module이 필요하다.

## 4. 2번 — 사용자 사용성
### 강점
- 한국어 표시와 Terminology Profile이 있다.
- 내부/고객 View를 선택할 수 있다.
- 미확정 정보 때문에 전체 Workflow를 막지 않는다.

### 한계
- `/setup`만 보면 사용자가 어떤 자료를 먼저 준비해야 하는지 Mode별 차이를 알기 어렵다.
- YAML/JSON/Profile/Overlay 개념을 모두 이해해야 Customizing 품질이 올라간다.
- `STARTABLE / DESIGN_READY / IMPLEMENTATION_READY`가 구분되지 않아 “자료를 얼마나 준비해야 하는가”가 모호했다.
- 사용자 역할별 Quick Path가 없다. 예: 고객 담당자, BA/설계자, 개발자, 운영자.

### 이번 보완
- `sdlc/starter-kits/greenfield`
- `sdlc/starter-kits/brownfield`
- `sdlc/design/contracts/starter-kit-contract.json`

Greenfield는 Source 없이도 시작 가능하고 Brownfield는 `analysis_seed + repository.reference`를 최소 기준으로 둔다.

### 잔여 개선
- `/setup` Wizard 또는 질문형 Bootstrap
- 역할별 `처음 10분 가이드`
- 문서별 `누가 작성/누가 검토/언제 승인` 표시
- Minimal/Standard/Strict Project Preset

## 5. 3번 — 저수준 Agent 재현성
현재 Reference Contract는 방향은 맞지만 상대적으로 강한 추론 능력을 전제로 한다.

예를 들어 Requirement Reference의 Steps는 `입력/Evidence 분리 → 최소 결과 → 미확정 표시 → Canonical 동기화` 수준이다. 약한 Agent에게는 다음이 추가로 필요하다.

### 필수 보완: Agent Execution Contract
각 Stage마다 최소 다음을 구조화해야 한다.
1. Input Field Schema
2. Precondition / Skip Condition
3. Retrieval Query 생성 규칙
4. Search Budget / Expansion Stop Rule
5. Evidence 분류 규칙: GIVEN / OBSERVED / INFERRED / ASSUMED / CONFIRMED
6. Canonical 생성/갱신 규칙
7. Template Placeholder별 채우는 방법
8. Confidence 산정 규칙
9. 실패/미확정 예시
10. Positive/Negative Few-shot Example
11. Quality Gate의 machine-checkable 조건
12. 다음 Stage 전달 필드

### 판정
**현재 상태만으로 저수준 Agent의 일관된 산출물/Source 생성을 보장하기 어렵다.** `GAP-AG-001`을 Core 필수 보완으로 둔다.

## 6. 4번 — Brownfield 영향도 분석
현재 `DISCOVERY`는 Source root를 적용하고 Symbol/Data 후보와 Locator를 수집하며, `IMPACT`는 Technical/Functional/Business Impact를 분리한다. 원칙은 적절하다.

하지만 실제 Brownfield 영향 분석에서 필요한 다음 관계 계약이 부족하다.
- Entry Point
- Caller / Callee
- Read / Write Data
- Transaction boundary
- DB Table/View/Procedure
- API / Message / Event consumer
- Scheduler / Batch
- Config / Feature Flag
- Module / Build dependency
- Test relation / coverage
- Reflection/Dynamic dispatch/Runtime wiring 사각지대

### 필요한 최소 구조: Impact Evidence Graph
Node 후보:
- SOURCE_FILE, SYMBOL, ENTRY_POINT, JOB, EVENT, CONFIG, DATA_ASSET, TEST, PGM, FR, RQ

Edge 후보:
- CALLS, CALLED_BY, READS, WRITES, PUBLISHES, SUBSCRIBES, CONFIGURED_BY, DEPENDS_ON, TESTED_BY, TRACES_TO

모든 영향 분석은 최소 다음 결과 클래스를 가져야 한다.
- `DIRECT_IMPACT`
- `INDIRECT_IMPACT`
- `CHECK_REQUIRED`
- `OUT_OF_SCOPE`

그리고 **Coverage Gap**을 결과의 일부로 반드시 보여줘야 한다. “찾지 못함”은 “영향 없음”과 다르다.

### 판정
**현재 Brownfield 영향 분석은 설계 원칙은 맞지만 Production 수준의 영향 누락 방지 계약은 부족하다. `GAP-BF-001`은 Core 우선 보완 대상이다.**

## 7. 5번 — Source 변경에서 이전 산출물 Reverse
현재 `/change`는 Source Evidence와 충돌하면 기존 설계/Knowledge를 `STALE` 처리할 수 있고, `implementation-result.md`는 변경 전/후 Source Hash와 설계 차이를 기록한다.

그러나 다음 파이프라인은 없다.

```text
Source Diff
  → Changed Symbol/Data/Interface 식별
  → Trace/Evidence Graph Diff
  → 영향받은 PGM/Functional Design/Process/BR Candidate 식별
  → Artifact/Canonical STALE 전파
  → Reverse Delta Candidate 생성
  → Human/Business Review
  → Canonical 승격
```

### 당장 필요한 최소 범위
- Source Hash/Symbol Diff 감지
- Source Evidence를 참조한 Artifact를 `STALE` 처리
- 어떤 문서/필드가 왜 stale인지 설명
- 자동 덮어쓰기 없이 Reverse Candidate 생성

이 최소 범위는 Brownfield 유지보수를 위해 Core에 필요하다.

### 고도화로 분리할 범위
- AST-level semantic diff
- 자동 문장 재작성
- Field-level provenance dependency
- Runtime trace와 Source diff 결합
- 여러 Branch간 Knowledge merge

### 판정
**자동 Reverse 갱신은 현재 미구현이다. 최소 Drift/STALE propagation은 Core 우선, 완전 자동 Reverse Rewrite는 고도화 영역으로 둔다.**

## 8. 6번 — Source에서 BR/Program Spec 추출
### Program Spec
Source에서 다음은 비교적 신뢰성 있게 관찰할 수 있다.
- Entry Point와 실제 Symbol
- Method signature / DTO technical shape
- Call relation
- Repository/Mapper/SQL
- Table/Column 후보
- Transaction annotation
- Exception/Logging 일부
- Security annotation 일부
- Test relation

따라서 **AS-IS Observed Program Spec**은 만들 수 있다.

하지만 현재 Program Spec은 Requirement/FR을 입력 전제로 한다. Brownfield 전체 Inventory나 Reverse 분석에서는 Requirement가 없는 Program도 존재하므로 다음 중간 모델이 필요하다.

`OBSERVED_PROGRAM → PGM_CANDIDATE → RQ/FR mapping(optional)`

### Business Rule
Source에서 다음은 `Observed BR Candidate`로 추출할 수 있다.
- 조건문에 의한 허용/거부
- Validation
- 상태 전이
- 계산식
- 임계값/상수
- Role/Permission check
- 특정 데이터 조건에 따른 분기

그러나 다음 이유로 Business Truth로 자동 확정할 수 없다.
- 버그/레거시 우회 코드일 수 있음
- Dead code일 수 있음
- Runtime Config에 따라 동작이 달라질 수 있음
- 정책 의도가 Source에 표현되지 않을 수 있음
- Source와 최신 업무 규정이 충돌할 수 있음

따라서 Source 기반 규칙은 다음 상태가 필요하다.
- `OBSERVED_BR_CANDIDATE`
- `INFERRED_BR_CANDIDATE`
- `CONFIRMED_BR`는 사람/권위 있는 업무 근거 필요

### 판정
- **Source→Observed Program Spec: 부분 가능, 구조 보완 필요**
- **Source→Business Rule Candidate: 가능**
- **Source→Confirmed Business Rule: 원칙적으로 자동화 불가**

## 9. Gap 우선순위
### P0 — 현재 SDLC 신뢰성 확보에 우선 필요
- `GAP-UX-001` Mode-specific Greenfield/Brownfield Starter Kit — 이번 Branch에서 1차 구현
- `GAP-AG-001` Low-level Agent Deterministic Execution Contract
- `GAP-BF-001` Brownfield Impact Evidence Graph + Coverage Contract
- `GAP-RE-001A` Source Drift Detection + Artifact STALE Propagation

### P1 — 다음 고도화 후보
- `GAP-AR-001` Stage-specific Artifact Content/Quality Contract
- `GAP-RE-001B` Reverse Delta Candidate generation
- `GAP-RE-002` Observed Program Inventory / Reverse Program Spec
- `GAP-BR-003` Source-derived Observed BR Candidate extraction
- Role-based Review Path / Minimal-Standard-Strict presets

### P2 — 프로젝트 필요 시 Adapter/고도화
- 언어별 AST/Call Graph 정밀 Adapter
- Reflection/Dynamic dispatch/Runtime trace
- Stored Procedure/Trigger/ETL 전용 분석
- OCR/Office 고급 Extraction Adapter
- Field-level provenance graph / semantic merge

## 10. 최종 권고
현재 v1.5.5를 그대로 “모든 Greenfield/Brownfield와 Reverse Engineering에 충분하다”고 확정하면 안 된다.

다음 의사결정 전까지 권장 상태는:
- Greenfield: **구조적 Pilot 가능**
- Brownfield: **Starter/Source 연결은 가능하지만 Impact Evidence Graph 보완 전 Production 영향 분석 신뢰성은 제한**
- Reverse Engineering: **설계 Gap으로 보존, 자동 지원을 주장하지 않음**
- Source→BR: **Candidate 추출만 허용, Business Truth 자동 승격 금지**
