## 이번 변경에서 직접 확인한 사항

### 1. Functional Design / Program Spec 책임 분리
- `developer-spec-contract.json`에서 Functional Design을 `SEMANTIC_SOURCE_OF_TRUTH`로 정의했다.
- Program Spec은 `IMPLEMENTATION_DELTA_AND_EXECUTION_READINESS`로 정의했다.
- Program Spec에서 기존의 6W 전체표, 화면 상세, Field 의미 상세, CRUD 의미 상세, 업무규칙 전체 재작성 Section을 제거했다.
- Program Spec은 기능 설계 기준점, 실제 구현 Target, 구현 Mapping/Delta, Query/Table/Source, Transaction, Integration 기술계약, Technical Control, TASK/AC/TC/Source, Readiness 중심으로 축소했다.

### 2. Program DoR 표현 축소
- 기존 17개 의미를 제거하지 않았다.
- 17개 별도 Section 요구를 제거하고 `### 구현 준비도` 한 개 표의 17개 행으로 바꿨다.
- `program-spec-readiness.json`과 `validate_program_spec.py`도 새 표현 방식에 맞췄다.

### 3. OPEN 사용자 UX 축소
- 기존 Machine status/category/domain/method/basis는 호환성을 위해 유지한다.
- 사람에게 보이는 상태는 `미확정 / 확인중 / 제안 / 확정 / 보류` 5개로 제한했다.
- `Decision Domain`, `Resolution Method`, `Basis Class`, 내부 status, downstream impact는 일반 사용자의 필수 입력에서 제외하고 Machine metadata로 이동했다.
- OPEN Workbook의 기본 표를 확인내용/확인방법/현재값·제안/담당/진행상태 중심으로 축소했다.

### 4. /setup 진입 축소
최초 입력을 다음 5개로 정의했다.
1. 프로젝트 유형
2. 요구사항/변경요청 위치
3. Source/Repository 위치
4. Build/Test 경로
5. 고객용 문서 필요 여부

나머지 Profile은 실제 필요 시 Advanced Setup에서 연다.

### 5. Reverse 기능 과대표현 방지
Harness capability 명칭을 `SOURCE_DRIFT_AND_REVERSE_REVIEW_CANDIDATE`로 명시했다.
전체 Reverse Engineering, Program Spec 자동 재생성, Business Truth 자동 역갱신은 구현된 것으로 간주하지 않는다.

## 실행하지 못한 검증

### Local unittest
현재 작업 환경에서 `github.com` DNS resolution이 실패하여 branch를 로컬 clone할 수 없었다.
따라서 `python -m unittest discover -s tests -v`는 실행하지 못했다.

이 사유는 테스트 성공을 의미하지 않는다.

### GitHub CI
현재 작업 head에 연결된 combined status와 workflow run을 조회했으나 확인 가능한 실행 결과가 없었다.
따라서 CI 성공으로 판단하지 않는다.
