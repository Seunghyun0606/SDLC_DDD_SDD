## 이번 변경에서 직접 확인한 사항

### 1. Requirement / Requirement Analysis 활성 산출물 통합
- 신규 DECOMPOSE Stage의 Template을 `requirement.md`로 변경했다.
- `requirement.md`가 원문/External ID/목표/Scope/FR/BR 후보/AC/OPEN을 한 문서에서 관리한다.
- `requirement-analysis.md`는 `DEPRECATED_COMPATIBILITY_VIEW`로 전환했다.
- Legacy View에는 FR/BR/AC를 재작성하지 않고 기준 `requirement.md`를 참조하도록 했다.

### 2. Functional Design / Program Spec 책임 분리
- `developer-spec-contract.json`에서 Functional Design을 `SEMANTIC_SOURCE_OF_TRUTH`로 정의했다.
- Program Spec은 `IMPLEMENTATION_DELTA_AND_EXECUTION_READINESS`로 정의했다.
- Program Spec에서 기존의 6W 전체표, 화면 상세, Field 의미 상세, CRUD 의미 상세, 업무규칙 전체 재작성 Section을 제거했다.
- Program Spec은 기능 설계 기준점, 실제 구현 Target, 구현 Mapping/Delta, Query/Table/Source, Transaction, Integration 기술계약, Technical Control, TASK/AC/TC/Source, Readiness 중심으로 축소했다.

### 3. Program DoR 표현 축소
- 기존 17개 의미는 유지한다.
- 17개 별도 Section 대신 `### 구현 준비도` 한 개 표의 17개 행으로 관리한다.
- `program-spec-readiness.json`과 `validate_program_spec.py`도 동일 표현을 검증한다.

### 4. OPEN 사용자 UX 축소
- 기존 Machine status/category/domain/method/basis는 호환성을 위해 유지한다.
- 사람에게 보이는 상태는 `미확정 / 확인중 / 제안 / 확정 / 보류` 5개다.
- `Decision Domain`, `Resolution Method`, `Basis Class`, 내부 status, downstream impact는 일반 사용자의 필수 입력에서 제외했다.

### 5. /setup 5문항 Fast Path + Preset 호환
최초 입력은 프로젝트 유형, 요구사항/변경요청 위치, Source/Repository 위치, Build/Test 경로, 고객용 문서 필요 여부 5개다.

기존 자동화 호환을 위해 Preset ID는 사용자 질문으로 노출하지 않고 내부 자동 Mapping으로 유지한다.
- `GREENFIELD → greenfield-default`
- `BROWNFIELD → brownfield-auto`

### 6. 고객문서 8종 → 3개 활성 View
활성 문서 유형을 다음 3개로 제한했다.
- `solution_agreement` — 요구·업무·기능 합의서
- `delivery_scope` — 영향·개발범위 공유서
- `acceptance_handover` — 테스트·인수·운영 결과서

3개 View가 INTAKE부터 KNOWLEDGE_PROMOTION까지 전체 Workflow를 덮는다. 기존 8개 customer document type ID는 삭제하지 않고 `legacy_document_aliases`로 3개 활성 View에 연결한다.

신규 활성 Template:
- `A01_요구_업무_기능_합의서.md`
- `A02_영향_개발범위_공유서.md`
- `A03_테스트_인수_운영_결과서.md`

### 7. 내부 Artifact → Customer View Projection Runtime
`render_customer_document.py`를 placeholder-only renderer에서 실제 Projection Runtime으로 변경했다.

입력:
- 내부 Markdown Artifact
- Canonical JSON Bundle
- 위 파일이 있는 Directory

기본 처리:
- Contract의 `projection_sections`, `base_section_sources`, `catalog_section_sources` 실행
- 담당 Stage의 내부 Artifact만 사용
- 최신 관련 Stage 우선
- 동일 내용 중복 제거
- 내부 RQ/FR/BR/PGM/TASK/AC/TC ID 숨김
- Source Hash/Locator/Confidence 숨김
- 내부 상태 코드의 고객용 한국어 표시 변환
- 근거가 없는 Section은 추정하지 않고 명시적 미확인 문구 출력

### 8. Reverse 기능 과대표현 방지
Harness capability 명칭은 `SOURCE_DRIFT_AND_REVERSE_REVIEW_CANDIDATE`다. 전체 Reverse Engineering, Program Spec 자동 재생성, Business Truth 자동 역갱신은 구현된 것으로 간주하지 않는다.
