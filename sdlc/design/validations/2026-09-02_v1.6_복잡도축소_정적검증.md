### 8. Canonical JSON Store + Delta Runtime
기존에는 `/work`, `/change`가 Canonical relation 갱신을 지시했지만 실제 공통 Store/apply Runtime이 없었다. `sdlc/scripts/apply_canonical_delta.py`를 추가하고 `/work`와 `/change`를 동일 실행 경로에 연결했다.

별도 신규 Contract는 추가하지 않았다. 기존 `harness-package-contract.json`에 Runtime capability만 등록했다.

지원 Operation은 3개다.
- `UPSERT_ENTITY`
- `UPSERT_RELATION`
- `ADD_PROVENANCE`

의도적으로 미지원:
- DELETE
- 자동 의미 병합
- 자동 Business Truth 역갱신
- Source write 승인

실행 경로:
`Stage/Change Artifact → 최소 Delta JSON → dry-run → apply → result/revision 확인 → Artifact trace/customer projection`

안전 규칙:
- optimistic `base_revision`
- 동일 `delta_id` idempotent
- all-or-nothing
- Relation endpoint 누락 fail-closed
- Entity type 충돌 fail-closed
- `CONFIRMED_BUSINESS` 신규/변경은 `CONFIRMED` Evidence 필요
- `OBSERVED / INFERRED / ASSUMED`는 `CONFIRMED_BUSINESS` 필드 덮어쓰기 금지
- Source-derived Evidence가 필드가 같더라도 `CONFIRMED_BUSINESS` 상태를 낮추는 것 금지
- 현행 Source 근거만 연결할 때 `ADD_PROVENANCE` 사용 가능

### 9. Reverse 기능 과대표현 방지
Harness capability 명칭은 `SOURCE_DRIFT_AND_REVERSE_REVIEW_CANDIDATE`다. 전체 Reverse Engineering, Program Spec 자동 재생성, Business Truth 자동 역갱신은 구현된 것으로 간주하지 않는다.

## 여전히 남은 검증
현재 범위에서 Customer Projection과 Canonical apply Runtime의 기본 동작은 실제 CI에서 검증했다. 그러나 다음은 아직 별도 검증이 필요하다.
- 저수준 Agent가 동일 입력으로 반복 실행할 때 Stage Artifact와 Canonical Delta가 동일/안정적으로 생성되는지
- Stage Artifact → Delta JSON을 자동 생성하는 공통 Runtime이 필요한지, 또는 Agent Output Contract만으로 충분한지
- 실제 Greenfield 프로젝트 전체 Workflow 사용성 Pilot
- 실제 Brownfield Repository 기반 영향분석 Pilot
- 실제 Java/Spring/MyBatis Project Impact Adapter
- Source → Program Spec semantic regeneration/diff

로컬 환경의 GitHub DNS 제약으로 로컬 clone 기반 전체 unittest는 수행하지 못했지만, 동일 전체 unittest가 GitHub Actions에서 138개 모두 통과했다.
