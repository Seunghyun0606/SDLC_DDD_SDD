# 한글 산출물 / 고객 커뮤니케이션 / BR Intake 구조 검증

## 검증 범위
- Core Template 11종의 사용자 표시 단락 한국어화
- Program DoR 17개 항목의 한국어 표시 + 기존 영문 판정 하위 호환
- Customer Document 8종 표준 Template
- Workflow 12 Stage의 Customer View 매핑
- 고객 문서 6개 필수 단락 + 선택 단락 Contract
- Customer Document Profile / Terminology Override
- BR Intake 최소 Manifest 및 provenance
- BR Candidate 원문/정규화 분리
- `BR_CONFLICT` 비자동 해결
- 문서 등록 계약과 Extraction Adapter 구현 경계
- 기존 Project/Domain Overlay의 구형 문서 heading 하위 호환

## 판정 기준
1. 내부 machine key와 Canonical ID가 유지되어야 한다.
2. 사용자 표시 단락에 기존 혼합 영문 heading이 남지 않아야 한다.
3. 모든 Workflow Stage가 고객 문서 유형으로 매핑되어야 한다.
4. 고객 필수 단락은 Optional catalog와 겹치지 않아야 한다.
5. 고객 Profile 기본값은 내부 ID/Source Hash/Confidence를 고객 본문에서 숨겨야 한다.
6. BR Intake는 원본 보존과 최소 provenance를 강제해야 한다.
7. BR 문서 메타데이터 부족은 non-blocking이어야 한다.
8. BR Candidate는 원본 document/locator/hash/confidence로 되돌아갈 수 있어야 한다.
9. 문서 간 충돌은 자동 확정하지 않아야 한다.
10. Extraction Contract 실패/불확실 상태가 업무 규칙 부재로 오인되지 않아야 한다.
11. v1.5.5 이전 Overlay가 구형 heading을 참조해도 새 한국어 heading으로 안전하게 해석되어야 한다.

## 파일럿
실제 `요구사항목록.xlsx`의 `RQ-CAND-0001 / REQ_TM_FL001~003`을 이용해 다음 사용자 View를 생성했다.
- 고객 요구사항 협의서
- 고객 기능 설계 협의서
- BR Intake Manifest
- `REQ_TM_FL003` BR Candidate 검토 예시

BR Candidate는 원문 `기본 근무스케줄에 따라 근무계획 생성 자동 저장`을 보존하고 자연어 규칙 후보를 별도로 만들며, 문서 권위가 `UNKNOWN`이므로 `REVIEW_REQUIRED`로 유지한다. 실제 Business Truth로 자동 승격하지 않는다.

## CI에서 발견한 하위 호환 이슈와 수정
첫 PR CI의 Worklist quality #116에서 기존 Workflow Pilot Overlay가 `## 본문` heading을 참조해 실패했다. v1.5.5 Core Template의 사용자 표시 heading이 `## 상세 내용`으로 변경된 것이 원인이었다.

기존 고객/프로젝트 Overlay를 깨뜨리지 않도록 `resolve_overlay.py`에 다음 heading alias를 추가했다.
- `## 30초 요약` → `## 한눈에 보기`
- `## Workflow` → `## 업무 흐름`
- `## 입력/Evidence` → `## 입력 및 근거`
- `## 본문` → `## 상세 내용`
- `## 미확정/Alert/Assumption` → `## 미확정 사항·주의·가정`
- `## 관련 ID/Traceability` → `## 관련 ID 및 추적성`

수정 commit은 `02375970610a61675adaed46b81b283873fc3ae0`이다.
