# v1.5.8 요구사항 기반 6W / 개발상세 Pilot 검증

## 검증 목적
첨부 `요구사항목록.xlsx` 142건을 기준으로 v1.5.8에서 도입한 6하원칙 업무 시나리오와 Developer-ready 상세설계 계약이 실제 요구사항 입력에서 어떤 효과를 내는지 평가한다.

## 입력 범위
- `REQ_TM_FL001~039`: 39건
- `REQ_TM_TE001~103`: 103건
- 합계: 142건
- 업무 영역: 근무계획, ESS, Report, 근태기록, 근태마감, 현황/통계, Batch, Interface, 메인화면
- 실제 Application Source / UI Spec / DB Schema / Common Code Dictionary / Interface Contract는 제공되지 않았다.

따라서 본 Pilot은 요구사항 자체가 제공하는 정보만 사용하고, Source가 필요한 항목은 `OPEN_REAL_SOURCE` 또는 `OPEN`으로 유지한다.

## 평가 방법
### 6W 상태
각 요구사항에 대해 다음 6개 관점을 `EXPLICIT / PARTIAL / OPEN`으로 평가했다.
- Who: 누가 수행하는가
- When: 언제/어떤 Trigger에서 수행하는가
- Where: 어떤 시스템/메뉴/화면/Job/API에서 수행하는가
- What: 무엇을 처리하는가
- How: 어떤 절차/CRUD/판단으로 수행하는가
- Why: 왜 이 업무가 필요한가

`PARTIAL`은 요구사항에 단서가 있으나 개발·업무 합의에 필요한 상세가 부족함을 뜻한다.

### 개발 상세 상태
v1.5.8 Developer Spec의 핵심 항목을 요구사항만으로 어느 정도 채울 수 있는지 평가했다.
- 업무 시나리오(6W)
- 화면/메뉴/컴포넌트
- 노출/입출력 필드
- CRUD
- 핵심 비즈니스 로직
- 데이터/조회/쿼리
- 공통코드/기준정보
- 연계
- 권한
- 예외/오류
- AC/TC

### 개발 상세
요구사항 목록만으로 상대적으로 명확한 것은 CRUD 유형이다.

반대로 다음은 전체 또는 거의 전체가 추가 Evidence를 필요로 했다.
- 화면 Field/DTO Field: 142건 `OPEN`
- 실제 Table/Column/Query/Mapper: 142건 `OPEN_REAL_SOURCE`
- 공통코드/기준정보: 142건 `OPEN`
- 예외/Error Contract: 142건 `OPEN`
- 권한: 109건 `OPEN`, 33건도 단서 수준 `PARTIAL`
- 연계: 25건은 송수신/메일/전자결재 등의 단서가 있으나 Contract는 `PARTIAL`, 나머지는 부재를 N/A로 확정할 근거가 없어 `OPEN`

따라서 **Developer READY는 0/142**이다.

## 대표 상세 Pilot
다음 7건을 유형별 대표로 선정했다.

| 요구사항 | 유형 | 검증 목적 |
|---|---|---|
| REQ_TM_FL001 탄력근로제 근무계획 저장 | UI/Create | 일반 화면 저장 기능 |
| REQ_TM_FL003 기본 근무스케줄에 따라 근무계획 생성 자동 저장 | Auto Logic | 자동 생성/업무규칙 |
| REQ_TM_FL018 예외사항 승인 전자결재 송신 | Integration | 승인/전자결재 연계 |
| REQ_TM_FL030 법정 근로시간 초과 검증 Report 조회 | Report | 검증 Rule + 조회/Query |
| REQ_TM_TE018 일근태입력/마감 신청 등록 | State/Create | 마감 상태/신청 Workflow |
| REQ_TM_TE080 구성원 표준 근무시간 초과 안내 매일 발송 | Batch/Notification | Who/When 단서가 비교적 많은 Batch |
| REQ_TM_TE100 구성원 근무계획 Yellow Page 송신 | Interface | 외부 Interface 송신 |

### 대표 관찰: REQ_TM_FL001
`탄력근로제 근무계획 저장`이라는 요구만으로는 What과 CREATE 행위는 식별할 수 있으나 다음은 알 수 없다.
- 실제 사용자 Role/Profile
- 언제 입력하는지
- 정확한 메뉴/화면 ID
- 날짜/시간 등 실제 입력 Field
- 저장 Validation
- 기존 계획 중복 처리
- Table/Column/Mapper
- 공통코드
- 권한 범위
- 오류/예외

따라서 6W 자연어 문장을 임의로 완성하면 안 되고, 누락 영역을 고객/SOP/Source 질문으로 돌려야 한다.

### 대표 관찰: REQ_TM_FL003
`기본 근무스케줄에 따라 근무계획 생성 자동 저장`은 일반 요구보다 핵심 로직 단서가 강하다. 그러나 다음은 여전히 `OPEN`이다.
- 기본 스케줄 선택 기준
- 최초 판단 조건
- 기존 근무계획이 있을 때 처리
- 자동 생성 시점/Trigger
- 중복 실행/Idempotency
- 생성 대상 날짜 범위
- 실패 시 재처리

즉 핵심 문구가 있어도 Decision Table과 구현 규칙을 만들기에는 부족하다.

### 대표 관찰: REQ_TM_FL018
`전자결재 송신`으로 Integration 자체는 식별 가능하지만 Target Endpoint, Payload, 인증, Timeout, Retry, 중복 송신, 수신 결과 처리, Error Contract는 알 수 없다.

### 대표 관찰: REQ_TM_FL030
`법정 근로시간 초과 검증 Report 조회`는 Why와 Business Rule 단서를 제공하지만 실제 법정 기준값/적용 대상/기간 계산/예외 대상/Query Source/Table/Join은 요구사항 목록에 없다.

### 대표 관찰: REQ_TM_TE080
`구성원 표준 근무시간 초과 안내 매일 발송`은 142건 중 6W 단서가 가장 충실한 편이다. 구성원(Who 후보), 매일(When), 초과 안내(Why/What), 발송(How)이 드러난다. 그러나 수신자 규칙, 발송 시각, 표준 근무시간 산식, 제외 대상, Mail Template, 실패/재발송은 여전히 `OPEN`이다.

## v1.5.8 설계 효과 평가
### 효과가 확인된 부분
1. 6W를 강제하자 기존 요구사항 목록의 부족한 업무 맥락이 즉시 드러났다.
2. What/CRUD만으로 설계가 충분하다고 오판하는 것을 막았다.
3. Functional/Program Spec에서 화면·Field·Query·Table·공통코드·권한·연계를 독립적으로 `OPEN` 처리할 수 있었다.
4. 요구사항에 없는 내용을 Agent가 자연스럽게 보완해 버리는 위험을 줄였다.
5. 고객/SOP/Source에서 어떤 Evidence를 추가로 받아야 하는지가 질문 목록으로 변환됐다.

### 여전히 보완이 필요한 부분
1. 6W의 `PARTIAL` 판정 기준을 프로젝트 적용 시 더 정교하게 정의할 필요가 있다. 예: `월별`이 업무 Trigger인지 단순 조회 기간인지 구분.
2. 사용자 Role/Profile과 실제 Screen/Menu 정보는 Starter Kit 또는 SOP Extraction에서 더 적극적으로 수집해야 한다.
3. Brownfield에서는 Source Adapter를 통해 Table/Query/Common Code/Integration을 실제 Evidence로 채우는 Pilot이 반드시 필요하다.
4. Greenfield에서는 승인된 UI/UX, Data Model, Common Code, Interface Design이 없으면 Developer READY가 될 수 없다.

## 최종 판정
**STRUCTURAL_IMPROVEMENT_PASS / REQUIREMENT_ONLY_DEVELOPER_READY_FAIL / PROJECT_EVIDENCE_REQUIRED**

v1.5.8의 방향 자체는 유효하다. 다만 첨부 요구사항 목록은 기능 카탈로그 성격이 강해, 이를 바로 개발 명세로 취급해서는 안 된다. 다음 단계는 동일 요구사항에 실제 SOP/정책 문서와 Brownfield Source 또는 Greenfield 승인 설계를 추가했을 때 `OPEN`이 얼마나 줄어드는지 비교하는 것이다.
