# v1.5.6 비판적 설계 검토 — Starter Kit / Brownfield / Reverse Engineering

## 검토 기준
단순히 Template/Skill 파일의 존재 여부가 아니라 다음 질문으로 평가했다.
- 사람이 실제로 작성·검토하기 쉬운가?
- 저수준 Agent가 같은 입력에서 유사한 품질을 재현할 수 있는가?
- Brownfield Source 관계 누락을 통제할 수 있는가?
- Source 변경으로 설계 산출물의 stale 상태를 역으로 추적할 수 있는가?
- Source에서 관찰한 기술 사실과 Business Truth를 혼동하지 않는가?

## 핵심 판정
| 검토 항목 | 판정 |
|---|---|
| 산출물 효과성 | 조건부 충족 — Program DoR/Trace/Evidence는 강함, Stage별 내용 계약 추가 필요 |
| 사용자 사용성 | 조건부 충족 — 한글/Customer View는 유효, Mode별 시작점 부족을 Starter Kit으로 1차 보완 |
| 저수준 Agent | 미충족에 가까운 조건부 — deterministic execution contract 필요 |
| Brownfield 영향 분석 | 미충족 — Impact Evidence Graph/Coverage contract 필요 |
| Source→이전 산출물 Reverse | 미충족 — Source Diff→STALE propagation pipeline 없음 |
| Source→Program Spec | 부분 가능 — Observed Program 모델 필요 |
| Source→Business Rule | Candidate 추출만 가능 — 자동 Business Truth 승격 금지 |

## Greenfield Starter 판정
최소 입력은 프로젝트 목적과 요구/문제 원문이다. Source는 필수가 아니다.

준비도는 `STARTABLE → DESIGN_READY → IMPLEMENTATION_READY`로 분리한다.

## Brownfield Starter 판정
최소 입력은 `analysis_seed.text + repository.reference`다. Source root/build/test는 탐색 가능하지만 Repository 기준점이 없으면 실제 Source 분석을 Confirmed로 표시할 수 없다.

Brownfield 영향 분석이 장기적으로 만족해야 할 관계는 Entry Point, Caller, Callee, Data Read/Write, Transaction, DB, Interface/Event, Config/Feature Flag, Test, Module/Build Dependency다.

## 안전 경계
- Source 구현은 Business Rule의 근거 후보이지 Business Truth 자체가 아니다.
- Reverse 결과는 자동 문서 덮어쓰기가 아니라 Candidate/STALE로 시작해야 한다.
- `찾지 못함`은 `영향 없음`으로 해석하지 않는다.
- Reference/Simulated Source는 Real Source Evidence를 만족하지 않는다.
