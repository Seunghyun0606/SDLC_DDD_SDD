# P0.6 Runtime / Provider Adapter Boundary 결과

> Branch: `SDLC_DESIGN_SESSION_SECOND/p0.6/runtime-provider-boundary-v1`  
> Base: `SDLC_DESIGN_SESSION_SECOND/p0.5/e2e-orchestration-v1`  
> 원칙: 첨부 요구사항목록 및 근태마감 Pilot은 **Sample/Regression Fixture일 뿐 Core Contract 설계 근거로 하드코딩하지 않는다.**

## 1. Verdict

**P0.6 RUNTIME/PROVIDER BOUNDARY: PASS WITH REAL ADAPTER IMPLEMENTATION OPEN**

P0.5까지의 SDLC 상태 계약을 실제 Tool/Runtime에 연결하기 위한 최소 Provider Boundary를 구현했다.

```text
/work | /change | /check
→ Required Capability
→ Provider Registry
→ Provider State + Capability exact match
→ Provider Request
→ Adapter / Tool
→ Provider Response + Evidence
→ 기존 P0.x Contract
```

이번 단계는 실제 고객 Source/Test/Canonical Tool Adapter를 구현한 것이 아니라, 어떤 Adapter도 같은 계약으로 연결할 수 있는 Runtime Boundary와 Guard를 정의한 단계다.

## 3. Core Provider Contract

### Provider Request

공통 필드:
- request ID
- provider type
- operation/capability
- project mode/stage
- target
- input
- write intent
- write proof
- extensions

### Provider Response

공통 필드:
- request correlation
- provider ID/type
- operation
- status
- provider revision
- outputs
- evidence
- open items
- warnings
- extensions

Source/Test Evidence는 Business Truth `CONFIRMED`로 자동 승격하지 않는다.

## 4. Capability 기반 Routing

Provider 선택 기준은 업무명/Framework/제품명이 아니다.

`<domain>.<resource>.<verb>` 형태의 Capability exact match를 사용한다.

예:
- `source.snapshot.read`
- `source.search`
- `source.diff`
- `test.discover`
- `test.execute`
- `canonical.id.reserve`
- `canonical.publish`
- `deployment.release.execute`

Router는 Capability가 없으면 자동 대체 구현을 추측하지 않는다.

## 5. Provider Type 확장성

초기 Core가 직접 사용하는 Type:
- SOURCE
- TEST
- CANONICAL_REGISTRY
- COMMAND_ROUTER

그러나 Validator는 닫힌 enum을 사용하지 않는다. 대문자 식별자 규칙을 만족하면 다음과 같은 Type을 Core Router 수정 없이 추가할 수 있다.

- DEPLOYMENT
- MONITORING
- NOTIFICATION
- ISSUE_PM
- BUSINESS_DOCUMENT

Router는 Provider Type switch/case가 아니라 Capability exact match로 동작한다.

Generic Conformance에서 `DEPLOYMENT + deployment.release.execute`를 추가하고 Core Router 변경 없이 READY가 되는 것을 검증했다.

## 6. Provider 선언과 실제 연결 분리

초기 구현 중 중요한 위험을 발견해 `provider_state`를 별도 도입했다.

States:
- AVAILABLE
- DEGRADED
- UNAVAILABLE
- UNCONFIGURED
- DISABLED

선택 가능한 것은 `enabled: true`이면서 `AVAILABLE/DEGRADED`인 Provider뿐이다.

따라서 Example Registry에 Source/Test slot이 있어도 실제 Adapter가 연결되지 않은 기본상태 `UNCONFIGURED`이면 실행 Provider로 선택하지 않는다.

결과:

```text
Capability 없음
→ MISSING_CAPABILITY

Capability 선언은 있음 + Adapter 미연결
→ PROVIDER_UNAVAILABLE
```

예제 파일이 실제 Runtime처럼 오인되는 문제를 차단한다.

## 7. Greenfield / Brownfield / Hybrid

### Greenfield

초기 DESIGN에서 Existing Source가 없다는 이유만으로 Source Provider를 강제하지 않는다.

Generic Case:

```text
GREENFIELD + DESIGN + /work
requested source capabilities = []
→ READY
```

### Brownfield

Discovery/Impact에서 Source Evidence가 필요하면 Stage가 명시적으로 Source Capability를 요청한다.

```text
BROWNFIELD + DISCOVERY
source.snapshot.read
source.search
→ AVAILABLE Source Provider 필요
```

### Hybrid

신규 영역과 Existing 영역이 요청하는 Capability를 Work Unit/Stage 단위로 구분한다. 프로젝트 전체를 Source Provider 유무 하나로 결정하지 않는다.

## 8. Generic Conformance — 비파일럿 사례

근태 Pilot과 독립적으로 다음 Case를 추가했다.

## 9. Pilot 요구사항 사용 범위

첨부 요구사항목록 기반 근태마감 사례는 이번 P0.6에서 다음 세 가지 Regression 기대만 확인한다.

1. `/check`는 Local Router만으로 상태 조회 계획을 만들 수 있음
2. 실제 고객 Source가 필요한 `/work`는 Example Source Provider가 UNCONFIGURED이므로 ACTION_REQUIRED
3. Runtime Test가 필요한 `/work`는 Example Test Provider가 UNCONFIGURED이므로 ACTION_REQUIRED

이 Sample에서 나온 Requirement ID, 업무명, Table, Java/MyBatis 구조는 Core Provider Schema/Router/Capability 정의에 사용하지 않았다.

## 10. Write Safety

Read Capability에서 Write를 암묵적으로 허용하지 않는다.

Write 요청 필수:
- explicit write capability
- READ_WRITE provider
- expected revision
- permission proof reference
- idempotency key
- non-ambiguous target

Canonical Publish는 추가로 P0.2 Human/L2 Boundary Decision과 ID reservation/preallocation이 필요하다.

## 11. Low-Agent Readiness

### L1 Agent 가능
- required capability 목록 처리
- exact provider matching
- provider state 확인
- request/response correlation 검사
- evidence field 검사
- missing/unconfigured provider를 OPEN으로 보존
- runtime plan 생성

### L2/Human 필요
- Business Boundary/Rule 결정
- Provider가 반환한 Evidence의 업무적 의미 판단
- Production 승인

### Engineering/L3 필요
- 실제 Provider Adapter 구현
- Runtime credential/permission 연결
- 복합 provider/runtime 오류 분석

## 13. Deterministic Guard

주요 차단 조건:

- Provider ID 중복
- Provider State invalid
- Capability naming invalid
- Write proof 누락
- usable Provider 없음
- Provider Request/Response correlation mismatch
- Source/Test Evidence의 CONFIRMED Business Truth 승격
- Response Provider가 Registry capability를 광고하지 않음
- UNCONFIGURED/UNAVAILABLE Provider Response
- Missing Capability
- Ambiguous Provider
- Pilot 고유 token의 Core Runtime 파일 하드코딩

## 14. Validation 상태

Repository에 반영한 동일 Validator/Router 로직을 세션의 독립 Python 실행으로 검증했다.

확인한 Positive:
- AVAILABLE Command Router → READY
- Greenfield DESIGN without Source → READY
- Brownfield Source capability → READY
- Test capability → READY
- 신규 DEPLOYMENT Provider Type → Core 변경 없이 READY

확인한 Negative:
- Monitoring provider 없음 → MISSING_CAPABILITY
- Source Provider UNCONFIGURED → PROVIDER_UNAVAILABLE
- Write proof 누락 → validation error
- Read-only Source에 Write intent → blocked
- SOURCE Evidence를 CONFIRMED로 승격 → blocked

실제 Repository checkout 기반 CI 실행은 이번 단계의 증거로 주장하지 않는다. 실제 Adapter/Tool invocation도 아직 수행하지 않았다.

## 15. 현재 제한사항

P0.6으로 해결되지 않은 것은 다음이다.

1. 실제 Source Provider 구현체
2. 실제 Test Provider 구현체
3. 실제 Canonical Registry/ID Provider
4. Provider authentication/secret handling implementation
5. 실제 Tool retry/timeout/circuit-breaker runtime
6. Command Router가 Chat Runtime에서 `/work /change /check`를 실제 invoke하는 Adapter
7. 실제 고객 Source/Test를 통한 Provider conformance

따라서 **Runtime Boundary는 준비됐지만 Runtime Integration은 아직 OPEN**이다.
