
## 7. Existing Fixture 문서와 교차검증

기존 Fixture CR에는 다음 정책이 명시되어 있다.

- 월마감 후 승인 수정요청은 재집계 허용
- 미승인/요청 없음은 재집계 금지
- FORCE_CLOSE는 승인 여부와 무관하게 재집계 금지

After-CR Source Diff는 이 조건들을 실제로 탐지했다.

기존 Impact Analysis는 `TB_ATT_CORRECTION_REQ` 신규 READ와 `TB_ATT_CLOSE` 월마감 조회 추가를 기록하고 있으며, P0.3 Diff 결과와 일치한다.

기존 Test Scenario도 다음 축을 포함한다.

- 10분 반영
- 월마감 + 승인 수정요청
- 월마감 + 미승인/요청없음
- 월마감 + FORCE_CLOSE

따라서 Synthetic Fixture에서 Reverse Sync가 Impact/PGM/Test를 STALE 후보로 올리는 정밀도는 적절했다.

## 8. Low-Agent / Deterministic Guard

### 자동 가능한 범위

- Direct Manifest Artifact 확인
- File SHA-256
- Java method 후보 추출
- Mapper statement 추출
- Table reference 추출
- Source Diff
- 신규 Mapper/Table signal
- Direct Program 기반 Technical STALE Candidate

### L2/Human이 필요한 범위

- Source의 조건이 실제 의도된 Business Rule인지 판단
- Candidate Group 39건 전체가 PGM 하나에 속하는지 실제 고객 Source에서 확정
- Business Requirement/BR/AC를 수정할지 결정
- Blind Spot이 실제로 없는지 최종 Impact completeness 판단

## 9. Validator Fail-safe

다음은 차단하도록 구현했다.

- File SHA-256 누락/오류 → `DISC-007`
- Source Evidence를 `CONFIRMED`로 입력 → `DISC-009`
- Before/After hash 동일인데 Changed File 선언 → `RS-005`
- BUSINESS_RULE_CANDIDATE인데 Human Truth 보호 없음 → `RS-011`
- Business Rule 후보인데 Human-capable Review 없음 → `RS-012`
- Requirement를 Source Diff만으로 자동 STALE → `RS-015`

## 10. Blind Spot / 미검증 범위

이번 P0.3으로 검증하지 못한 것은 다음과 같다.

1. 실제 고객 Repository
2. 전체 Call Graph completeness
3. 다른 Service/Batch 호출자
4. Oracle Procedure/Trigger
5. Runtime-only dependency
6. 외부 Consumer
7. 실제 Build/Test 실행
8. 실제 Source Write 권한/Transaction Recovery
9. 실제 Canonical Registry write

따라서 `PGM-ATT-CLOSE-001` 관계는 **Synthetic Fixture 내부에서만 Direct/Confirmed Technical Relation**이다. 실제 고객 소스 관계로 승격하면 안 된다.

## 13. 다음 단계

실제 Source가 없다면 다음으로 진행 가능한 안전한 범위는 두 가지다.

1. Fixture에 존재하는 Test/Verification 자산을 이용해 Synthetic `TEST → VERIFY` 계약을 검증한다.
2. 실제 고객 Repository가 제공되면 동일 Discovery/Impact/Reverse Sync pipeline을 실제 Source로 재실행한다.

실제 고객 Source 없이 Production Source Write를 모사하여 성공 판정을 만들지는 않는다.
