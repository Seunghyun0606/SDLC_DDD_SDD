# 사람에게 보여주는 표현 가이드

이 문서는 Agent가 HITL 질문과 사람용 문서를 만들 때 사용하는 표현 기준이다.
내부 Runtime/Contract의 상태 코드나 식별자는 유지할 수 있지만, 사용자에게는 쉬운 한국어를 우선한다.

기준 Contract: `sdlc/design/contracts/human-facing-language-contract.json`

## 1. 기본 원칙

1. 사람이 알아야 할 **사실 → 영향 → 결정할 내용 → 다음 행동** 순서로 쓴다.
2. 내부 상태명이나 영문 Taxonomy를 그대로 질문 제목이나 표 머리글로 사용하지 않는다.
3. 기술 용어가 꼭 필요하면 없애지 말고 첫 등장에 쉬운 설명을 붙인다.
4. 한 문장 안에 영문 약어와 내부 코드를 여러 개 나열하지 않는다.
5. 사용자에게 문서 Template이나 내부 JSON 구조를 이해하도록 요구하지 않는다.
6. 사용자가 답하지 못하면 쉬운 표현으로 `보류`라고 안내하고, 내부적으로만 `DEFERRED` 상태를 사용한다.

## 2. 자주 바꿔 써야 하는 표현

| 내부/전문 표현 | 사람에게 보여줄 표현 |
|---|---|
| `DEFERRED` | 보류 |
| `OPEN` | 확인 필요 |
| `ANALYZING` | 확인 중 |
| `PROPOSED` | 제안 |
| `SOURCE_BLOCK` | 개발 전 확인 필요 |
| `ITERATE` | 진행 가능·추후 보완 |
| `ALERT` | 주의 필요 |
| `Recheck At` | 다시 확인할 시점 |
| `Human Decision Queue` | 추가 확인이 필요한 사항 |
| `Queue ID` | 질문 번호 |
| Business Truth | 확정된 업무 기준 |
| Canonical | 기준 정보 |
| Canonical Delta | 기준 정보 변경 내용 |
| Projection | 생성 문서 |
| Provenance | 근거 이력 |
| Evidence | 근거 |
| Locator | 근거 위치 |
| Confidence | 신뢰 수준 |
| Semantic Work | 현재 작업 |
| Stage | 작업 단계 |
| Source Write | 소스 수정 |
| Write Scope | 수정 가능 범위 |
| Guard | 안전 확인 |
| Authority | 결정 권한 |
| Artifact | 산출물 |
| topology | 문서 구성 |
| 영속적 | 저장 후 계속 유지되는 |
| 영속성 | 저장 및 유지 |

Framework를 설명하는 가이드에서는 첫 등장에만 `기준 정보(Canonical)`처럼 병기할 수 있다. 일반 HITL 질문과 생성 문서 본문에는 한국어 표현만 쓰는 것을 기본으로 한다.

## 3. 문장 예시

피해야 하는 표현:

- `이 값은 DB에 영속적인가요?`
- `이 결정은 DEFERRED로 둘까요?`
- `SOURCE_BLOCK이므로 Recheck At을 DEVELOPMENT로 둘까요?`
- `Canonical Delta를 만들고 Projection을 갱신합니다.`

권장 표현:

- `이 값은 처리 후 DB에 저장되어 계속 유지되어야 하나요?`
- `지금 결정하기 어렵다면 보류하고 다음 작업에서 다시 확인할까요?`
- `이 내용은 개발 전에 확인해야 합니다. 개발 시작 전에 다시 확인할까요?`
- `확정된 내용을 프로젝트 기준 정보에 반영한 뒤 생성 문서를 최신 내용으로 갱신합니다.`

## 4. HITL 질문 형식

사용자에게는 다음 항목만 간단히 보여준다.

```text
[질문 1]
왜 확인이 필요한가: 승인 후 취소 가능 여부에 따라 저장 로직과 테스트 기준이 달라집니다.
현재 확인한 내용: 현재 시스템은 승인 후 취소 기능이 없습니다.
확인이 필요한 내용: 개선 후에는 승인 후 취소를 허용할까요?
선택 가능한 내용: ① 허용하지 않음 ② 관리자만 허용 ③ 모든 승인 담당자에게 허용
답하지 못할 때 처리: 지금 결정하지 않아도 됩니다. 다만 개발 전에 다시 확인해야 합니다.
다시 확인할 시점: 개발 시작 전
```

내부적으로 같은 질문을 `HITL-<TARGET>-<NN>`, `DEFERRED`, `SOURCE_BLOCK`, `BEFORE_SOURCE_WRITE` 등에 연결할 수 있지만 사용자가 그 코드를 이해해야 답할 수 있는 질문을 만들면 안 된다.

## 5. 문서 작성 규칙

- 제목과 표 머리글은 가능한 한 한국어 명사형으로 짧게 쓴다.
- 상태는 `확인 필요 / 확인 중 / 제안 / 보류 / 확정`을 사용한다.
- 개발 영향은 `개발 전 확인 필요 / 진행 가능·추후 보완 / 주의 필요`를 사용한다.
- `AS-IS`, `TO-BE`, `CRUD`처럼 프로젝트에서 흔히 쓰는 약어도 사용자 대상 문서에서는 첫 등장에 `현재(AS-IS)`, `개선 후(TO-BE)`, `조회·등록·수정·삭제(CRUD)`처럼 뜻을 함께 쓴다.
- DB/Source 기술 표현이 업무 담당자에게 필요하지 않으면 구현 문서로 내리고 업무 문서에서는 업무 의미만 남긴다.
- `영속적`, `영속성`처럼 개발자에게는 익숙해도 일반 사용자에게 낯선 용어는 `DB에 저장되어 유지되는`, `DB 저장 여부`처럼 풀어 쓴다.

## 6. 질문 전 자체 점검

Agent는 사용자에게 질문이나 문서를 보여주기 전에 다음을 확인한다.

- 내부 상태 코드가 그대로 노출되어 있지 않은가?
- 사용자가 기술 용어의 뜻을 알아야만 답할 수 있는 질문인가?
- `왜 필요한지`가 한 문장으로 설명되어 있는가?
- 사용자가 지금 답하지 못해도 다음 행동이 이해되는가?
- 같은 뜻을 이전 문서와 다른 용어로 쓰고 있지 않은가?

하나라도 맞지 않으면 질문 또는 문장을 쉬운 한국어로 다시 작성한다.
