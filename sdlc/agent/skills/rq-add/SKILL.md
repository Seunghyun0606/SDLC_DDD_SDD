# SDLC Core Skill — rq-add

이 Skill은 프로젝트 진행 중 새 요구사항이 한 건 또는 소수 추가되었을 때 요구사항 Excel을 다시 Intake하지 않고 **사용자의 자연어 요청을 새 RQ 후보로 안전하게 추가**하기 위한 Core Skill이다.

## 1. 사용자 요청 예

다음 요청은 이 Skill로 처리한다.

```text
새 RQ 추가해줘. 승인 완료된 근무계획은 일반 사용자가 수정할 수 없게 해줘.
요구사항 하나 추가해줘: 퇴직자도 과거 급여명세서를 조회할 수 있어야 해.
/rq-add 승인된 신청 건은 취소할 수 없게 해줘.
```

조금 더 정보를 주고 싶다면:

```text
새 RQ 추가해줘.
- 요구사항명: 승인 전 연차신청 취소
- 요청 내용: 직원이 승인되기 전에는 연차신청을 취소할 수 있게 해줘.
- 현재 문제/배경: 잘못 신청하면 담당자에게 취소를 요청해야 해.
- 기대 결과: 본인이 직접 취소하고 사용 예정 연차가 다시 사용 가능해야 해.
- 적용 범위: 연차신청
```

사용자는 RQ ID, Sequence, Canonical Delta, JSON을 직접 만들 필요가 없다.

## 2. 언제 사용하고 언제 사용하지 않는가

### 사용

- 최초 Intake 이후 새 요구사항이 한 건 추가됨
- 회의/메신저/고객 요청에서 새 요구사항이 자연어로 들어옴
- Excel을 다시 만들 정도가 아닌 소수의 추가 요구사항

### 사용하지 않음

- 기존 `RQ-001`의 정책/범위/요구 내용을 변경 → `/change`
- 여러 행의 요구사항 목록을 한 번에 추가 → `harness.py intake <requirements.xlsx>`
- Source/DB/Program의 현재 사실을 추가 조사 → `/work`
- PM 담당자/일정/우선순위만 변경 → `/rq-list`

**기존 RQ 변경과 새 RQ 추가를 구분하지 못한 상태에서 새 RQ를 만들어 중복시키지 않는다.** 사용자가 기존 RQ ID를 명시하며 내용을 바꾸는 요청이면 `/change`가 우선이다.

## 3. RQ 생성에 필요한 기초정보

### 최소 입력

RQ 하나를 만드는 데 사용자가 반드시 제공해야 하는 의미 정보는 다음 두 가지다.

1. **요구사항명** — 작업목록에서 구분하기 쉬운 짧은 이름
2. **요청 내용** — 무엇을 새로 만들거나 바꾸고 싶은지 적은 원문

단, 사용자가 요청 내용을 충분히 설명했는데 제목만 생략한 경우 Agent는 **원문의 의미를 넓히지 않는 짧은 제목**을 만들 수 있다. 그러므로 실제 대화에서는 요청 내용 한 문장만으로도 시작할 수 있다.

### 있으면 좋은 정보

다음은 있으면 초기 분석 품질이 좋아지지만 RQ 생성을 막는 필수 항목은 아니다.

- **현재 문제/배경**: 지금 무엇이 불편하거나 왜 필요한지
- **기대 결과**: 완료 후 사용자가 어떤 결과를 기대하는지
- **적용 범위**: 알고 있는 업무/화면/기능 범위
- **외부 요구 ID**: 고객 요구관리번호 등이 이미 있을 때만

모르면 `OPEN`으로 남기고 후속 `/work`에서 조사/질문한다. Agent가 빈칸을 채우기 위해 업무 사실을 발명하지 않는다.

### RQ 생성 시 넣지 않아도 되는 정보

- RQ 번호/Sequence → Runtime이 관리
- Java Class/Method/Table/Query → `/work`에서 조사
- 담당자/일정/WBS/PM 우선순위 → `/rq-list`에서 관리
- 확정 Business Rule → 알고 있는 경우 근거로 제공할 수 있지만, 모르면 후속 분석/확인
- 참고문서 연결 → RQ 생성 후 `/rq-ref`로 연결

## 4. 공식 Runtime 진입점

Agent는 사용자 자연어에서 요청 원문과 짧은 제목을 준비하고 다음 공식 명령을 사용한다.

```bash
python sdlc/scripts/harness.py rq-add \
  --title "근무계획 승인 후 수정 제한" \
  --request "승인 완료된 근무계획은 일반 사용자가 수정할 수 없게 해줘."
```

기초정보가 더 있으면 함께 전달한다.

```bash
python sdlc/scripts/harness.py rq-add \
  --title "승인 전 연차신청 취소" \
  --request "직원이 승인되기 전에는 연차신청을 취소할 수 있게 해줘." \
  --background "잘못 신청하면 담당자에게 취소를 요청해야 한다." \
  --desired-result "본인이 직접 취소하고 사용 예정 연차를 다시 사용할 수 있다." \
  --scope "연차신청"
```

고객/외부 요구 ID가 명확히 주어진 경우에만 `--external-id`를 추가한다.

원문 한 줄만으로도 실행 가능하다.

```bash
python sdlc/scripts/harness.py rq-add "승인 완료된 근무계획은 일반 사용자가 수정할 수 없게 해줘."
```

## 5. 반드시 보존하는 것

- 사용자가 말한 요구 원문은 `original_requirement`로 보존한다.
- 새 RQ는 내부적으로 `CANDIDATE`로 시작한다.
- 사용자 직접 요청은 `GIVEN` 근거로 남기지만, 이것만으로 세부 Business Rule 전체를 확정하지 않는다.
- `current_problem`, `desired_result`, `scope`, `business_rules`처럼 아직 확인되지 않은 상세 의미는 임의로 채우지 않고 확인 필요 상태로 둔다.

예:

```text
사용자: "승인된 건은 수정 못하게 해줘"

보존:
- 원문: 승인된 건은 수정 못하게 해줘
- 제목: 승인 후 수정 제한

임의 생성 금지:
- 승인 주체는 팀장이다
- 관리자만 예외 수정 가능하다
- 승인 후 24시간 뒤 잠긴다
```

## 6. RQ 번호와 현재 단일 작성자 정책

현재 RQ 번호는 별도 중앙 Sequence Server가 아니라 **현재 `sdlc/canonical/store.json`에 있는 `RQ-NNN`의 최대 번호를 확인해 다음 번호를 선택**한다.

```text
RQ-001
RQ-002
RQ-003
→ 새 요구사항은 RQ-004
```

따라서 현재 운영 정책은 다음과 같다.

- RQ 생성 담당자는 **한 명**으로 운영한다.
- 여러 Agent/사람이 동시에 `rq-add`를 실행하지 않는다.
- Runtime이 번호를 선택하고 Canonical write는 lock/Revision Guard로 보호한다.
- 만약 다른 쓰기와 충돌하면 자동으로 번호를 재선점/재시도하지 않고 `RQ_ADD_CONFLICT_RETRY_REQUIRED`로 중단한다.
- 충돌 시 앞 작업이 끝난 뒤 RQ 생성 담당자가 현재 상태에서 다시 실행한다.

여러 사람이 동시에 RQ를 생성하는 중앙 Sequence/Reservation 방식은 현재 Runtime 범위가 아니며 Framework TODO로 관리한다.

## 7. 중복 처리

동일 요청 원문 또는 동일 요구사항명이 이미 있으면 기본적으로 새 RQ를 만들지 않고 중복 확인을 요청한다.

유사한 문장이라는 이유만으로 자동 병합하지 않는다. 실제 별도 RQ가 맞다고 확인했을 때만 `--allow-duplicate`를 사용할 수 있다.

외부 요구 ID가 이미 다른 RQ에 사용 중이면 자동 덮어쓰기나 자동 병합을 하지 않고 실패시킨다.

## 8. 기본 Flow

```text
사용자 새 요구사항
→ 기존 RQ 변경인지 새 RQ인지 구분
→ 요청 원문/기초정보 정리
→ 기존 중복 후보 확인
→ 현재 파일에서 다음 RQ 번호 선택
→ harness rq-add
→ 새 RQ 분석 전 상태 생성
→ Canonical Revision Guard 적용
→ PM RQ 작업목록 자동 refresh
→ 생성된 RQ ID + 아직 확인할 정보 보고
→ 필요 시 /work로 분석 시작
```

## 9. 성공 후 사용자에게 보여줄 내용

Machine JSON 전체보다 다음을 우선한다.

```text
새 요구사항을 RQ-014로 추가했습니다.
- 제목: 근무계획 승인 후 수정 제한
- 상태: 분석 전 요구사항
- 원문: 승인 완료된 근무계획은 일반 사용자가 수정할 수 없게 해줘.
- 아직 확인할 내용: 기대 결과, 적용 범위
- RQ 작업목록도 최신화했습니다.
- 다음 작업: RQ-014 분석
```

사람에게 `CANDIDATE`, `GIVEN`, Canonical revision 같은 내부 용어를 이해하도록 요구하지 않는다.

## 10. 추가 직후 자동으로 하지 않는 것

RQ 추가 자체는 다음을 자동 수행하지 않는다.

- Source 분석
- Business Rule 확정
- Change Level 강제 확정
- 개발
- 고객문서 최종화

사용자가 `추가하고 바로 분석해줘`라고 명시하면 RQ 추가 성공 후 새 Target으로 `/work`를 이어서 수행할 수 있다.

## 11. 여러 새 요구사항을 자연어로 받은 경우

명확히 분리된 소수 요구사항이면 RQ 생성 담당자가 순서대로 각각 한 번씩 `rq-add`를 호출할 수 있다. 각 RQ의 원문을 섞지 않는다.

대량 목록, Excel 표, 수십 건의 요구사항이면 기존 Intake를 사용한다.

```text
소수 자연어 추가 → /rq-add
대량/정형 요구사항 → /intake
기존 RQ 의미 변경 → /change
```

## 12. 안전 규칙

- `sdlc/canonical/store.json`을 직접 편집하지 않는다.
- 기존 RQ를 새 요청으로 덮어쓰지 않는다.
- 현재는 한 명의 RQ 생성 담당자만 `rq-add`를 실행한다.
- 유사 문장 자동 병합 금지.
- 외부 요구 ID 중복 자동 해결 금지.
- 원문을 보기 좋게 바꾼 문장을 원문 대신 저장하지 않는다.
- 제목 생성 과정에서 조건/예외/정책을 추가하지 않는다.
- 추가 성공 후 PM 작업목록 refresh 실패가 나더라도 이미 적용된 RQ를 임의 롤백하지 않는다. 실패한 관리 View만 다시 갱신한다.

상세 사용법은 `docs/00_시작/17_RQ_간편추가_가이드.md`를 따른다.
