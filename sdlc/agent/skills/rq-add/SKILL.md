# SDLC Core Skill — rq-add

이 Skill은 프로젝트 진행 중 새 요구사항이 한 건 또는 소수 추가되었을 때 요구사항 Excel을 다시 Intake하지 않고 **사용자의 자연어 요청을 새 RQ 후보로 안전하게 추가**하기 위한 Core Skill이다.

## 1. 사용자 요청 예

다음 요청은 이 Skill로 처리한다.

```text
새 RQ 추가해줘. 승인 완료된 근무계획은 일반 사용자가 수정할 수 없게 해줘.
요구사항 하나 추가해줘: 퇴직자도 과거 급여명세서를 조회할 수 있어야 해.
/rq-add 승인된 신청 건은 취소할 수 없게 해줘.
```

사용자는 RQ ID, Canonical Delta, JSON을 직접 만들 필요가 없다.

## 2. 언제 사용하고 언제 사용하지 않는가

### 사용

- 최초 Intake 이후 새 요구사항이 한 건 추가됨
- 회의/메신저/고객 요청에서 새 요구사항이 자연어로 들어옴
- Excel을 다시 만들 정도가 아닌 소수의 추가 요구사항

### 사용하지 않음

- 기존 `RQ-001`의 정책/범위/요구 내용을 변경 → `/change`
- 여러 행의 요구사항 목록을 한 번에 추가 → `harness.py intake <requirements.xlsx>`
- Source/DB/Program의 현재 사실을 추가 조사 → `/work`
- PM 담당자/일정/우선순위만 변경 → `/rq-list`

**기존 RQ 변경과 새 RQ 추가를 구분하지 못한 상태에서 새 RQ를 만들어 중복시키지 않는다.** 사용자가 기존 RQ ID를 명시하며 내용을 바꾸는 요청이면 `/change`가 우선이다.

## 3. 공식 Runtime 진입점

Agent는 사용자 자연어에서 `원문 요청`과 짧은 `표시 제목`만 준비하고 다음 공식 명령을 사용한다.

```bash
python sdlc/scripts/harness.py rq-add \
  --title "근무계획 승인 후 수정 제한" \
  --request "승인 완료된 근무계획은 일반 사용자가 수정할 수 없게 해줘."
```

고객/외부 요구 ID가 명확히 주어진 경우에만 함께 전달한다.

```bash
python sdlc/scripts/harness.py rq-add \
  --external-id "HR-NEW-017" \
  --title "근무계획 승인 후 수정 제한" \
  --request "승인 완료된 근무계획은 일반 사용자가 수정할 수 없게 해줘."
```

원문 한 줄만으로도 실행 가능하다.

```bash
python sdlc/scripts/harness.py rq-add "승인 완료된 근무계획은 일반 사용자가 수정할 수 없게 해줘."
```

하지만 Agent는 가능하면 사람이 목록에서 알아보기 쉬운 짧은 제목을 함께 만든다. 제목은 원문의 의미를 확장하거나 새로운 정책을 추가하지 않는 중립적인 요약이어야 한다.

## 4. 반드시 보존하는 것

- 사용자가 말한 요구 원문은 `original_requirement`로 보존한다.
- 새 RQ는 `CANDIDATE`로 시작한다.
- 사용자 직접 요청은 `GIVEN` 근거로 남기지만, 이것만으로 세부 Business Rule 전체를 `CONFIRMED_BUSINESS`로 만들지 않는다.
- `current_problem`, `desired_result`, `business_rules`처럼 아직 확인되지 않은 상세 의미는 임의로 채우지 않고 확인 필요 상태로 둔다.

즉 다음처럼 처리한다.

```text
사용자: "승인된 건은 수정 못하게 해줘"

보존:
- 원문: 승인된 건은 수정 못하게 해줘
- 제목: 승인 후 수정 제한

임의 생성 금지:
- 승인 주체는 팀장이다
- 관리자만 예외 수정 가능하다
- 승인 후 24시간 뒤 잠긴다
```

원문에 없는 조건은 후속 `/work` 조사 또는 HITL 확인에서 다룬다.

## 5. ID와 중복 처리

Runtime이 현재 Canonical의 `RQ-NNN`을 확인해 다음 사용 가능한 번호를 만든다.

```text
RQ-001
RQ-002
RQ-003
→ 새 요구사항은 RQ-004
```

Agent가 RQ ID를 임의 계산해 직접 Canonical 파일을 편집하지 않는다.

동일한 직접 요청이 이미 이 Skill로 추가된 경우에는 새 RQ를 또 만들지 않고 기존 Target을 반환한다.

외부 요구 ID가 이미 다른 RQ에 사용 중이면 자동 덮어쓰기나 자동 병합을 하지 않고 실패시킨다. 유사한 문장이라는 이유만으로 기존 RQ와 자동 병합하지 않는다.

## 6. 기본 Flow

```text
사용자 새 요구사항
→ 기존 RQ 변경인지 새 RQ인지 구분
→ 원문 보존
→ 중립적인 짧은 제목 준비
→ harness rq-add
→ 중복/외부 ID 확인
→ 새 RQ Candidate 생성
→ Canonical revision 안전 적용
→ PM RQ 작업목록 자동 refresh
→ 생성된 RQ ID 보고
→ 필요 시 /work로 분석 시작
```

## 7. 성공 후 사용자에게 보여줄 내용

Machine JSON 전체보다 다음을 우선한다.

```text
새 요구사항을 RQ-014로 추가했습니다.
- 제목: 근무계획 승인 후 수정 제한
- 상태: 분석 전 요구사항
- 원문: 승인 완료된 근무계획은 일반 사용자가 수정할 수 없게 해줘.
- RQ 작업목록도 최신화했습니다.
- 다음 작업: RQ-014 분석
```

사람에게 `CANDIDATE`, `GIVEN`, Canonical revision 같은 내부 용어를 이해하도록 요구하지 않는다.

## 8. 추가 직후 자동으로 하지 않는 것

RQ 추가 자체는 다음을 자동 수행하지 않는다.

- Source 분석
- Business Rule 확정
- Change Level 강제 확정
- 개발
- 고객문서 최종화

사용자가 `추가하고 바로 분석해줘`라고 명시하면 RQ 추가 성공 후 새 Target으로 `/work`를 이어서 수행할 수 있다.

## 9. 여러 새 요구사항을 자연어로 받은 경우

명확히 분리된 소수 요구사항이면 각각 한 번씩 `rq-add`를 호출할 수 있다. 각 RQ의 원문을 섞지 않는다.

대량 목록, Excel 표, 수십 건의 요구사항이면 기존 Intake를 사용한다.

```text
소수 자연어 추가 → /rq-add
대량/정형 요구사항 → /intake
기존 RQ 의미 변경 → /change
```

## 10. 안전 규칙

- `sdlc/canonical/store.json`을 직접 편집하지 않는다.
- 기존 RQ를 새 요청으로 덮어쓰지 않는다.
- 유사 문장 자동 병합 금지.
- 외부 요구 ID 중복 자동 해결 금지.
- 원문을 보기 좋게 바꾼 문장을 원문 대신 저장하지 않는다.
- 제목 생성 과정에서 조건/예외/정책을 추가하지 않는다.
- 추가 성공 후 PM 작업목록 refresh 실패가 나더라도 이미 적용된 RQ를 임의 롤백하지 않는다. 실패한 관리 View만 다시 갱신한다.
