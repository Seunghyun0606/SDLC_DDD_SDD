## 검토 목적
업무 분석·설계 문서가 실제 업무를 충분히 설명하는지, 개발자가 기능/프로그램 문서만으로 구현 범위를 이해할 수 있는지, PPTX/XLSX/PDF 등 다양한 고객 SOP/Business Rule 문서를 일관된 추출 기준으로 활용할 수 있는지 검토한다.

## 1. 업무정의 6하원칙
### 기존 문제
기존 PROCESS는 Actor/Trigger/AS-IS/TO-BE를 다뤘지만 `누가/언제/어디서/무엇을/어떻게/왜`를 하나의 업무 Scenario 계약으로 강제하지 않았다. 특히 Why는 Source 구현만으로 추정할 위험이 있었다.

### 개선
Core 공통계약 `business-scenario-sixw-contract.json`을 추가했다.
- Who: Actor, Role/Profile, 권한/대상자
- When: Trigger, 주기, 시점, 마감/유효조건
- Where: System/Channel/Menu/Screen/Process 위치
- What: Business Object, Field/Scope, 기대 결과
- How: Procedure, CRUD, Validation/Decision, State Change
- Why: Business Purpose/의무/기대 결과

PROCESS → DESIGN → PROGRAM이 동일 Scenario ID를 추적한다.

누락된 항목은 `OPEN`으로 두며 상식/Source 구현으로 발명하지 않는다. Source 관찰은 Why를 자동 CONFIRMED하지 않는다.

### 예시 형식
`ESS 프로파일 권한을 가진 탄력근로제 근무자가(누가) 매일 근무계획 입력 시(언제) 탄력근로제 근무계획 메뉴에서(어디서) 근무 날짜와 시작/종료 시간을(무엇을) 선택하여 저장한다(어떻게). 이는 근무자가 예정 근무시간을 등록해야 하기 때문이다(왜).`

위 문장은 형식 예시이며 실제 프로젝트 Business Truth는 근거/확인이 필요하다.

## 2. 개발자가 이해 가능한 기능/프로그램 상세설계
### 기존 문제
기존 Functional Design은 I/O, Data, Transaction, Auth, Interface를 큰 단락으로 묶었고 Program Spec도 DTO/Data/Transaction 계약은 강했지만 다음 구현 판단이 충분히 분해되지 않았다.
- 화면/Menu/Component
- 노출/입력 Field
- CRUD
- 핵심 Business Logic 실행 순서
- Query WHERE/JOIN/ORDER/GROUP/PAGING
- 실제 Table/Mapper
- Common Code/기준정보
- 다른 Program/System Integration

### 개선
`developer-spec-contract.json`을 추가하고 DESIGN/PROGRAM Template을 강화했다.

필수 개발 상세 차원:
1. 6W Business Scenario
2. Entry Surface
3. UI Layout(해당 시)
4. Field Catalog
5. CRUD Matrix
6. Core Logic/Decision Table
7. Query/Data
8. Common Code/Reference Data
9. Integration
10. Security/Profile/Authorization
11. Error/Validation/AC/TC

상태는 `RESOLVED / OPEN / NOT_APPLICABLE`이며 N/A는 사유가 필수다.

기존 17-field Program DoR는 유지한다. 신규 Program Spec에 `개발 상세 명세 완성도`가 존재하면 상세 OPEN이 남아 있는 상태에서 READY를 허용하지 않도록 `validate_program_spec.py`를 강화했다.

### Core와 Project 책임 경계
Core가 제공하는 것은 **무엇을 설계해야 하는지와 품질 계약**이다.

실제 프로젝트에서 필요한 근거:
- UI: Screen/Menu/Route Source 또는 승인 UI 설계
- Field: UI/DTO/Validation/API/DB
- CRUD: Entry Point/Service/Repository
- Query/Table: Mapper/SQL/Schema/Migration
- Common Code: Code Table/Enum/Dictionary/기준정보 API
- Integration: API Client/Event Producer·Consumer/File/Batch

따라서 Project Evidence가 없으면 OPEN이며 임의 생성하지 않는다.

## 3. SOP/PPTX/XLSX 기반 Business Rule 추출
### 검토 결론
사용자 제안처럼 **추출 대상 Template과 사전 Prompt를 가진 Skill을 먼저 정의하고, 각 SOP에서 동일 기준으로 Candidate를 추출하는 방식이 더 적합하다.**

단, 실제 파일 Parsing과 의미 추출은 분리해야 한다.

### 1단계 — Format Adapter/Tool
PDF/DOCX/PPTX/XLSX/OCR에서 Evidence Chunk를 만든다.

`br-document-extraction-contract.json` v2는 다음을 보존한다.
- document_id
- locator
- raw_text
- source_hash
- extraction_status/method
- content_kind
- structured_content
- format_context

특히 XLSX Cell/Table 관계와 PPTX Slide/Shape/Table 관계를 가능한 한 보존한다.

### 2단계 — SOP Semantic Extraction Skill
`.cursor/skills/sop-extract/SKILL.md`에 사전 Prompt를 내장했다.

추출 대상:
- 6W Business Scenario
- Actor/Role/Profile/권한
- Trigger/주기/Deadline
- Procedure/Process
- Business Rule condition/action/outcome/exception
- State/Approval/Escalation
- Data/Field
- Common Code/Reference Value
- Screen/Menu/Form
- Integration/Event/API/Batch/File
- Audit/Control/SLA/Cutoff
- Conflict/Ambiguity/Clarification

출력은 SCN/PROC/BR/FR/DATA/SCREEN/INTEGRATION/CLARIFICATION Candidate이며 모든 Candidate는 원문 Locator/Hash로 돌아갈 수 있어야 한다.

Source/SOP 문장을 `CONFIRMED_BR`로 자동 승격하지 않는다.
