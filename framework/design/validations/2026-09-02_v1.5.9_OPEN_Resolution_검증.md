# v1.5.9 OPEN Resolution Template 검증

## 검증 목적
실제 프로젝트에서 SOP나 상세 선행문서가 없어도 설계자/개발자가 요구사항의 미확정 항목을 인터뷰, 기존 시스템 분석, Source/Data 분석, Project Standard, 전문경험 기반 제안으로 구조적으로 채워갈 수 있는지 검증한다.

## 이전 요구사항 Pilot의 재해석
v1.5.8 요구사항 142건 Pilot에서 `Developer READY = 0`과 다수 OPEN이 확인되었다.

이 결과를 `SOP/추가 문서가 반드시 필요하다`로 해석하면 현재 Harness 목표와 맞지 않는다.

정확한 해석은 다음과 같다.

> 요구사항만으로 모든 상세값이 사전에 확정되지는 않지만, Harness는 OPEN을 해소할 정형 Template과 작업 경로를 제공해야 한다.

따라서 기존 `PROJECT_EVIDENCE_REQUIRED`는 다음처럼 정교화한다.

`RESOLUTION_INPUT_OR_DECISION_REQUIRED`

여기서 Resolution Input은 문서만 의미하지 않는다.
- 고객/업무담당자 인터뷰
- Workshop
- 기존 시스템 화면/동작 분석
- Source/DB/Data 분석
- Project Standard
- 설계자 제안
- 개발자/Architect 기술 제안·결정
- QA 분석
이 모두 허용된다.

## Core 공통계약
### OPEN은 Actionable Design Backlog
각 OPEN은 최소 다음을 가진다.
- OPEN ID / 관련 RQ·FR·SCN·PGM
- Category
- Decision Domain
- 질문 또는 Gap
- Resolution Method
- Basis Class
- 관찰/제안 값
- Evidence 또는 Rationale
- Decision Owner Role
- Resolution Status
- Downstream Impact

### 해소 상태
- `OPEN`: 아직 해소 경로만 있거나 시작 전
- `ANALYZING`: 현행/Source/Data 분석 중
- `CANDIDATE`: 입력/근거에서 후보 식별
- `PROPOSED`: 설계자/개발자 제안안 존재
- `OBSERVED_AS_IS`: Brownfield 현행 동작 확인
- `ACCEPTED_DESIGN`: 프로젝트 권한자가 Target 설계로 채택
- `CONFIRMED_BUSINESS`: 업무 권한자가 Business Truth/정책으로 확인
- `CONFLICT`: 근거/결정 충돌
- `DEFERRED`: 후속 단계로 명시적 이월
- `N_A`: 비적용 + 사유

## Truth와 Design Decision 분리
### 설계자/개발자 경험
전문경험을 사용하는 것을 금지하지 않는다. 오히려 Greenfield 또는 문서가 부족한 프로젝트에서는 중요한 해소 수단이다.

다만 다음처럼 기록한다.
- Designer: `DESIGN_PROPOSAL`
- Developer/Architect: `TECHNICAL_PROPOSAL`

업무 정책을 포함하는 제안은 Business/Functional 권한자가 확인해야 한다.
기술/데이터/연계 설계는 Project Authority Profile이 허용하면 고객 확인 없이 `ACCEPTED_DESIGN`으로 해소할 수 있다.

### Brownfield 현행분석
Source/기존 시스템에서 확인한 동작은 `OBSERVED_AS_IS`다.
현행 시스템이 잘못 구현되었을 수도 있으므로 TO-BE 정책으로 자동 승격하지 않는다.

## 사람 중심 Template
`open-resolution-workbook.md`는 다음 영역을 포함한다.
1. OPEN 해소 목록
2. 6하원칙 업무정의 해소표
3. 화면·필드·CRUD 해소표
4. 업무 규칙·상태·예외 해소표
5. 데이터·조회·공통코드 해소표
6. 연계·권한·NFR·테스트 해소표
7. 결정 기록

`interview-questions.md`도 질문만 나열하지 않고 다음을 포함하도록 강화했다.
- 왜 필요한 질문인지
- 현재 알고 있는 내용
- 권장 선택지/예시
- 답변에 따라 변경되는 설계 영역
- 답변/결정권자 역할
- 인터뷰 없이 분석으로 해소할 항목
- 설계자/개발자 제안 항목

## Greenfield
SOP/Source 없이도 정상 시작한다.

우선 경로:
- Business/Why/Auth → 인터뷰/Workshop
- UI/Field/Flow → Designer Proposal
- API/Transaction/Query/Error/Integration/NFR → Developer/Architect Proposal + Project Standard

즉 Greenfield의 목표는 상세 문서를 고객에게 선제 작성시키는 것이 아니라, Harness Template을 설계자가 채워가며 Target Design을 만드는 것이다.

## Brownfield
SOP가 없어도 Repository가 있으면 AS-IS OPEN을 상당 부분 줄일 수 있다.

우선 경로:
- Screen/Menu/Field → 기존 화면/UI Source 분석
- CRUD/API/Service → Source 분석
- Table/Query/Common Code → Schema/Mapper/Data 분석
- Business Why/정책 → 인터뷰/Workshop
- TO-BE UI → Designer Proposal
- TO-BE Query/Transaction/Error → Developer Proposal + Project Standard

## RQ-CAND-0001 예시
`REQ_TM_FL001~003`을 대상으로 실제 OPEN 해소 예시를 작성했다.

사용자가 제시한 `ESS 프로파일 탄력근로자 / 매일 / 근무계획 메뉴 / 날짜·시간 / 저장 / 매일 근무시간 입력 필요`는 `PROPOSED` 업무정의 후보로 기록했다.

이 예시를 Business Truth로 확정하지 않고 다음과 같이 분리했다.
- Who/When/Why → Business Owner 확인
- Menu/Field/UX → Designer Proposal + Functional/UX Owner
- Query/Table/Common Code → Brownfield Source/Data 분석 또는 Greenfield Developer Proposal
- Transaction/Error → Developer Proposal + Technical Owner

## Project Customization 경계
Core는 Category/Method/Status/Template을 제공한다.

프로젝트별로 달라지는 것은 `open-resolution-profile.yaml`의 Authority Matrix다.
예:
- 업무 정책 확인권자
- UX 최종 결정권자
- Architecture/Technical Owner
- Data Owner
- Integration Owner
- QA/Acceptance Owner

따라서 Core가 특정 조직의 승인 체계를 강제하지 않는다.

## 결론
