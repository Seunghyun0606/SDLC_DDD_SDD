# v1.5.5-rc.1 — 한글 산출물 / 고객 커뮤니케이션 / 비정형 BR Intake Delta

## 1. 문제
1. 내부 산출물의 영어/Agent 중심 용어가 Agent에 익숙하지 않은 설계자·개발자에게 어렵다.
2. 내부 설계 문서를 고객 협의에 그대로 사용하기에는 기술 문맥이 강하고 고객/프로젝트별 선택성이 부족하다.
3. 고객이 보유한 규정, 계약, 매뉴얼, 회의록, 엑셀, 슬라이드 등 비정형 문서를 BR 입력으로 어떤 형태로 제공해야 하는지 표준 Intake 계약이 없다.
4. 비정형 문서 등록 계약과 PDF/DOCX/XLSX/PPTX 등의 실제 추출 구현이 구분되지 않으면 지원 범위를 과장할 수 있다.

## 2. 변경 설계

### 2.1 사람 친화적 내부 산출물
- Canonical ID와 machine metadata는 안정성을 위해 유지한다.
- 사용자에게 보이는 제목, 단락, 표 머리글, 질문, 설명은 한국어 자연어를 기본으로 한다.
- 모든 Core Template의 사용자 표시 단락을 한국어 표준 8개 단락으로 통일한다.
- RQ/FR/BR/PGM/TASK/AC/TC/DoR 같은 약어는 첫 등장 시 `기능 요구사항(FR)`처럼 한국어 의미를 함께 표시한다.
- Program DoR 17개 항목의 깊이는 유지하면서 표시 명칭만 한국어화한다.

### 2.2 고객 커뮤니케이션 View
- 고객 문서는 내부 Canonical 및 단계 산출물에서 파생되는 View이며 별도의 Business Truth Store가 아니다.
- `/work` 문서 대상은 `internal`, `customer`, `both`를 지원한다.
- 고객 문서 공통 필수 단락은 다음 6개로 고정한다.
  1. 문서 목적
  2. 한눈에 보기
  3. 고객과 함께 확인할 내용
  4. 합의된 내용
  5. 미확정 사항
  6. 다음 단계
- 다음 내용은 고객/프로젝트 Profile에서 선택한다: 요청 배경, 현재/개선 비교, 업무 영향, 범위/제외범위, 결정 필요사항, 테스트/인수기준, 일정/역할, 위험/대응, 운영 인수, 기술 상세 부록, 근거 상세 부록.
- Source Hash, Confidence, 내부 ID, 상세 기술정보는 고객 본문에서 기본 숨김이며 필요할 때 부록으로 활성화한다.
- 고객별 표현 차이는 Terminology Profile의 display term만 바꾸며 Canonical ID는 유지한다.

### 2.3 비정형 고객문서 BR Intake
고객에게 기존 문서를 BR Template로 다시 작성하도록 요구하지 않는다.

```text
br-input/
├─ originals/                 # 고객 원본, 변경 금지
├─ manifest.yaml              # 최소 문서 등록표
├─ context.md                 # 선택: 프로젝트 배경/범위
├─ glossary.csv               # 선택: 고객 용어/약어
└─ decisions/                 # 선택: 승인/결정 이력
```

최소 Manifest는 문서당 `document_id + path`만 요구한다. 제목, 종류, 권위, 유효상태, 담당부서, 적용일, 업무범위, 프로세스, 시스템, locator 힌트는 권장값이며 모르면 `UNKNOWN`으로 둔다.

정규화된 BR Candidate는 다음을 분리한다.
- 원문(`original_text`)
- 자연어 정리본(`normalized_statement`)
- 적용 조건
- 수행 주체
- 행동/판단
- 결과
- 예외
- 적용 기간
- 원본 문서 + 정확한 위치 + Source Hash + Confidence
- 관련 RQ/FR/Process/System
- 충돌 그룹 및 검토 상태

서로 다른 문서가 상충해도 자동으로 하나를 정답으로 선택하지 않고 `BR_CONFLICT`로 고객/업무 담당자 확인에 남긴다.

### 2.4 문서 추출 Adapter 경계
- 비정형 문서의 **등록 포맷 지원**과 **내용 추출 구현 지원**을 분리한다.
- 공통 Extraction Contract의 출력은 `document_id`, `locator`, `raw_text`, `source_hash`, `extraction_status`, `extraction_method`를 요구한다.
- PDF/DOCX/XLSX/PPTX/OCR 등 Adapter는 프로젝트/도구 Overlay에서 교체 가능하다.
- 신뢰성 있는 추출이 불가능하면 `EXTRACTION_REQUIRED` 또는 `PARTIAL`로 남기고 내용을 발명하지 않는다.

## 3. 표준 고객 산출물 유형
| Workflow | 고객 View |
|---|---|
| INTAKE / DECOMPOSE / CLARIFY | 요구사항 협의서 |
| PROCESS | 업무 프로세스 협의서 |
| DISCOVERY / IMPACT | 영향 범위 협의서 |
| DESIGN | 기능 설계 협의서 |
| PROGRAM / DEVELOPMENT | 개발 범위 및 구현 결과 공유서 |
| TEST | 테스트 및 인수 협의서 |
| VERIFY | 검증 및 승인 결과서 |
| KNOWLEDGE PROMOTION | 운영 인수 가이드 |

## 4. 호환성
- RQ/FR/BR/PGM/TASK/AC/TC Canonical ID는 변경하지 않는다.
- Source Evidence marker(`Locator`, `Source Hash`, `Confidence`, `Status`)는 한국어 표시와 함께 유지한다.
- v1.5.4의 Program Readiness 17-field contract를 유지한다.
- Program readiness validator는 한국어 표시와 기존 영문 표시를 모두 인식한다.
- 프로젝트 Custom은 기존 Core → Preset → Project Profile → Project Overlay → Domain Overlay → Local Override 구조를 그대로 사용한다.
